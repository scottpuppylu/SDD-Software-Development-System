# M4.2 Evaluation Contract v1

## 1. Status and authority boundary

This document is planning authority input for M4.2 Blocker 8 only. It defines the evaluation comparator, measurement boundaries, reuse reasons, controlled corpus, comparison rubric, evidence location, and evaluation statuses. It does not authorize M4.2 implementation, production-code changes, test changes, provider-boundary reuse, telemetry-schema changes, or persistent machine evaluation metadata.

M4.2 evaluation is a controlled comparison of fresh exact `BASELINE` assembly and execution against an explicit `OPTIMIZED` attempt for the same logical request. Safety and equivalence are proved first; optimization effects are observed second. No efficiency result can compensate for authority coverage below 100%, any authority byte mismatch, semantic regression, lifecycle regression, or gate regression.

The default remains `BASELINE`. `OPTIMIZED` means an attempt, not a guarantee. The comparison does not reconstruct or reopen Blockers 1–7.

## 2. Comparator and comparison identity

Every controlled case MUST have a fresh exact `BASELINE` comparator assembled and, where execution is part of the case, executed in the same controlled comparison scope as the explicit `OPTIMIZED` attempt. The two sides MUST use the same logical request, source inputs, stage coordinate, currently supported task coordinate, configuration, code revision, canonicalization contract, deterministic fixtures, and provider/executor configuration where provider execution is compared.

The fresh exact `BASELINE` result is mandatory. A prior run, cached result, historical result, semantic summary, digest-only assertion, or previously retained baseline cannot replace it. Observational IDs, timestamps, and stochastic provider wording are not logical comparison identity.

## 3. Measurement boundaries

All fields below are planning/evaluation-local. They do not amend telemetry schema 1.0.4.

### 3.1 Source and assembly

| Field | Frozen meaning |
| --- | --- |
| `source_context_utf8_bytes` | Sum of canonical UTF-8 bytes of every component occurrence produced by current fresh exact source assembly, counted once at its component boundary. |
| `source_component_count` | Exact integer count of those source component occurrences. |

### 3.2 Selection

| Field | Frozen meaning |
| --- | --- |
| `selected_context_utf8_bytes` | Sum of canonical UTF-8 bytes of every occurrence selected for the candidate effective ordered input, counted once. |
| `selected_component_count` | Exact integer count of selected occurrences. |
| `selection_excluded_component_count` | Exact integer count of source occurrences not selected into the candidate. |
| `selection_reason_counts` | Exact integer count by deterministic primary reason assigned under Section 5; the counts are evaluation explanations, not authority classifications. |

### 3.3 Authority

| Field | Frozen meaning |
| --- | --- |
| `authority_required_component_count` | Exact count of source occurrences subject to exact authority equivalence. |
| `authority_present_component_count` | Exact count of required occurrences with exactly one unambiguous effective occurrence at the required coordinate and ordered position; byte equality is separate. |
| `authority_missing_component_count` | Exact count of required occurrences with no corresponding effective occurrence at the required coordinate and ordered position. |
| `authority_duplicate_component_count` | Exact count of required occurrences for which more than one effective occurrence corresponds or may correspond. |
| `authority_byte_mismatch_count` | Exact count of present, uniquely mapped required occurrences whose canonical UTF-8 bytes differ. Missing and duplicate occurrences retain their structural counts and independently fail equivalence. |
| `authority_coverage` | Exact structural ratio defined by the authority-equivalence contract. It is 100% only for the required total bijection, order, and absence of ambiguity; it is never rounded into PASS. |

### 3.4 Baseline and delta

The `unchanged`, `changed`, `added`, and `removed` occurrence categories are mutually exclusive. `reordered` is an independently reported positional condition and MUST NOT be silently folded into or double-counted as another occurrence category. A case report MUST make any overlap between positional and content categories explicit.

| Field | Frozen meaning |
| --- | --- |
| `unchanged_component_count` | Exact count of unambiguous one-to-one occurrences with the same complete identity, exact canonical bytes, and preserved required effective position. |
| `changed_component_count` | Exact count of occurrences with the same complete identity but different exact canonical bytes. |
| `added_component_count` | Exact count of complete identities occurring only in current fresh exact assembly. |
| `removed_component_count` | Exact count of complete identities occurring only in the valid candidate baseline. |
| `reordered_component_count` | Exact count of corresponding occurrences whose required effective position changed where order affects effective input. |
| `unchanged_repeated_utf8_bytes` | Sum of current canonical component bytes for occurrences classified `unchanged`, each counted once. This is a local repeated-byte measurement, not avoided provider bytes. |
| `delta_utf8_bytes` | Sum of canonical component-content bytes that the exact component changeset must supply from current fresh exact assembly, each supplied occurrence counted once. Removed occurrences contribute no current component-content bytes; representation, identity, and control overhead are excluded and MUST NOT be silently included. |
| `reuse_eligible_utf8_bytes` | Sum of canonical source component bytes assigned an eligible component-level reuse reason, counted once. |
| `reuse_ineligible_utf8_bytes` | Sum of canonical source component bytes assigned an ineligible component-level reuse reason, counted once. |

`reuse_eligible_utf8_bytes` and `reuse_ineligible_utf8_bytes` partition the evaluated current source occurrences after deterministic reason assignment. They are not provider-savings measurements. Candidate-level reasons have zero component bytes and therefore do not disturb that partition.

### 3.5 Reconstruction

| Field | Frozen meaning |
| --- | --- |
| `reconstruction_component_count` | Exact integer count of occurrences in the complete reconstructed sequence. |
| `reconstruction_exact_match` | Boolean true only when the complete ordered identities, occurrences, canonical bytes, component count, authority coverage, and authority byte mismatch exactly satisfy the fresh exact assembly invariant. |

### 3.6 Provider and regression

| Field | Frozen meaning |
| --- | --- |
| `provider_unchanged_bytes_avoided` | Provider-bound bytes actually not transmitted while effective ordered provider input remains exactly equal to fresh exact assembly, and only when demonstrable under the Blocker 6 boundary. Under the current unsupported boundary it is unavailable/not proven, or zero only when zero is a factual observation under applicable measurement semantics. |
| actual provider input tokens | Reportable only with Blocker 9 valid provider-reported usage evidence. This contract does not define that validity test. |
| `semantic_regression_count` | Exact integer count of controlled comparisons that exhibit at least one semantic regression under Section 7. Multiple observed differences within one comparison MUST be listed but count as one regressed comparison. |
| `lifecycle_regression_count` | Exact integer count of controlled comparisons that exhibit at least one lifecycle regression under Section 8. |
| `gate_regression_count` | Exact integer count of controlled comparisons that exhibit at least one gate regression under Section 8. |

## 4. Byte and count semantics

Component bytes are canonical UTF-8 bytes under the approved canonicalization ID and rules already frozen by prior contracts. Exact inclusion and equivalence require direct canonical-byte comparison; digest equality alone is insufficient.

Source, selected, baseline/delta, reconstruction, and provider fields are distinct measurement lenses. Values MUST NOT be summed across those families as though they were disjoint savings. Within a field, each qualifying occurrence is counted once except that `reordered_component_count` is an explicitly separate positional count. Provider bytes are bytes at the actual provider boundary, not local manifest, delta, reconstruction, rendering, serialization, or other representation bytes.

All counts are deterministic non-negative integers. Ratios retain exact numerator and denominator; rounding MUST NOT produce a passing value. For an empty required authority set, authority coverage is 100% only under the empty-set and no-anomaly rule already frozen by the authority-equivalence contract.

## 5. Deterministic reuse reason taxonomy

Reasons explain evaluation eligibility or ineligibility. They do not create or change authority classification, inclusion authority, omission authority, semantic ranking, or precedence among instructions.

### 5.1 Eligible reasons

- `SAME_IDENTITY_EXACT_BYTES`: component-level; the occurrence has one unambiguous matching complete identity, exact canonical bytes, and preserved required position, and no ineligible rule below applies.
- `EXACT_RECONSTRUCTION_ELIGIBLE`: candidate-level; all baseline, identity, order, delta, reconstruction, and authority validations pass for the whole candidate. It does not itself contribute component bytes.

### 5.2 Ineligible reasons

- `ALWAYS_REQUIRED`: the component must remain included by the approved selection contract.
- `AUTHORITY_PROTECTED_EXACT`: exact authority treatment forbids treating the occurrence as avoidable or substitutable.
- `UNKNOWN_FAIL_CLOSED`: an `UNKNOWN` occurrence requires exact fail-closed treatment.
- `MIXED_AUTHORITY_FAIL_CLOSED`: a `MIXED_AUTHORITY` occurrence requires exact fail-closed treatment.
- `IDENTITY_MISMATCH`: complete identities do not match.
- `CONTENT_CHANGED`: the same complete identity has different canonical bytes.
- `COMPONENT_ADDED`: the occurrence exists only in current fresh exact assembly.
- `COMPONENT_REMOVED`: the occurrence exists only in the candidate baseline.
- `ORDER_CHANGED`: the required effective position changed.
- `DUPLICATE_IDENTITY`: one-to-one identity correspondence is defeated by a duplicate.
- `COLLISION_OR_AMBIGUITY`: collision simulation or another identity/content correspondence ambiguity prevents exact pairing.
- `BASELINE_INVALID`: baseline provenance, coordinate, lifetime, metadata, freshness, or other required validity failed.
- `AUTHORITY_CONFLICT`: an existing authority conflict blocks the affected implementation.
- `PROVIDER_REUSE_UNSUPPORTED`: current provider boundary cannot avoid retransmission while preserving the required effective input.

### 5.3 Assignment rule

Each current source occurrence receives exactly one primary component-level reason for byte partitioning. The deterministic precedence is:

1. `AUTHORITY_CONFLICT`;
2. `DUPLICATE_IDENTITY`;
3. `COLLISION_OR_AMBIGUITY`;
4. `BASELINE_INVALID`;
5. `IDENTITY_MISMATCH`;
6. `COMPONENT_ADDED` or `COMPONENT_REMOVED`, according to the compared side;
7. `CONTENT_CHANGED`;
8. `ORDER_CHANGED`;
9. `UNKNOWN_FAIL_CLOSED`;
10. `MIXED_AUTHORITY_FAIL_CLOSED`;
11. `AUTHORITY_PROTECTED_EXACT`;
12. `ALWAYS_REQUIRED`;
13. `PROVIDER_REUSE_UNSUPPORTED` when the evaluated proposition is provider-bound reuse;
14. `SAME_IDENTITY_EXACT_BYTES`.

All applicable secondary reasons MUST remain visible in case evidence; precedence only prevents byte double-counting. `EXACT_RECONSTRUCTION_ELIGIBLE` is recorded once for an eligible whole candidate. Unknown, mixed, malformed, duplicate, conflicting, or ambiguous states fail closed; reasons never bless omission or semantic substitution.

## 6. Controlled corpus

Each row is a deterministic fixture with its own mandatory fresh exact `BASELINE` comparator and explicit `OPTIMIZED` attempt. Expected outcomes are planning expectations; implementation closure later MUST instantiate them without inventing unsupported identity.

| Case | Expected deterministic outcome |
| --- | --- |
| Same stage, all unchanged | Exact categories and reasons; complete reconstruction exact; all safety regressions zero. |
| Same stage, one changed component | One exact `changed` occurrence and `CONTENT_CHANGED`; exact delta reconstructs fresh assembly or pre-dispatch fallback occurs. |
| Component added | One exact `added` occurrence and `COMPONENT_ADDED`; exact reconstruction or pre-dispatch fallback. |
| Component removed | One exact `removed` occurrence and `COMPONENT_REMOVED`; exact reconstruction only if permitted; required authority removal fails closed. |
| Ordering change | Exact reordered occurrences and `ORDER_CHANGED`; no silent sequence acceptance; exact reconstruction or pre-dispatch fallback. |
| Stage change | Full-baseline invalidation with `BASELINE_INVALID`; optimized call count zero and fresh `BASELINE` dispatch at most once. |
| Explicit task identity absent | Use the approved absent-task coordinate; deterministic comparison without invented task identity. |
| Task identity present | `NOT CURRENTLY EXECUTABLE` future-case placeholder; no task identity or runtime behavior is invented. This placeholder does not count as an executed passing case. |
| Duplicate identity | `DUPLICATE_IDENTITY`; full-baseline invalidation and fail-closed fallback behavior. |
| Empty string | Preserve its distinct canonical state and deterministic identity/content result. |
| Empty mapping | Preserve its distinct canonical state and deterministic identity/content result. |
| Empty list | Preserve its distinct canonical state and deterministic identity/content result. |
| Absent fixed input | Preserve absence as distinct from present-empty and null. |
| Explicit null where representable | Preserve explicit null as distinct from absent and present-empty. |
| `UNKNOWN` component | Exact fail-closed inclusion/equivalence with `UNKNOWN_FAIL_CLOSED`; no omission or transformation. |
| `MIXED_AUTHORITY` component | Exact fail-closed inclusion/equivalence with `MIXED_AUTHORITY_FAIL_CLOSED`; no omission or transformation. |
| Authority conflict | `AUTHORITY_CONFLICT`; affected implementation remains blocked and fallback does not hide a shared failure. |
| Identity mismatch | `IDENTITY_MISMATCH`; full-baseline invalidation and fail-closed behavior. |
| Simulated identity/digest collision | `COLLISION_OR_AMBIGUITY`; digest equality cannot establish equivalence; full-baseline invalidation. |
| Stale baseline | `BASELINE_INVALID`; optimized call count zero and fresh `BASELINE` dispatch at most once. |
| Missing baseline | `BASELINE_INVALID`; optimized path is unavailable/inapplicable and fresh `BASELINE` remains the comparator and dispatch path. |
| Invalid reconstruction | `reconstruction_exact_match == false`; partial optimized dispatch forbidden; discard candidate and fresh `BASELINE` may dispatch once. |
| Optimization-specific pre-dispatch failure | Optimized call count zero; discard candidate; fresh `BASELINE` may dispatch exactly once; no lifecycle or gate regression. |
| Provider reuse unsupported | `PROVIDER_REUSE_UNSUPPORTED`; no provider-savings result or claim; safety comparison remains executable locally. |
| `BASELINE` default compatibility | Unset/default and explicit `BASELINE` preserve the existing exact behavior and result meaning. |

Repeated identical deterministic fixtures MUST compare equal. An unexecuted mandatory current case makes the evaluation `INCOMPLETE`; an explicitly non-executable future placeholder does not authorize behavior and MUST be reported as a known limitation.

## 7. Semantic comparison rubric

Exact authority coverage and byte equivalence are independent prerequisites and cannot be replaced by semantic comparison. Missing, duplicate, reordered, ambiguous, transformed, or byte-mismatched authority fails its exact check even if outputs appear similar.

Deterministic comparison of validated `StageExecutionResult` fields and deterministic artifacts comes first. For each applicable case it MUST compare the observable meaning relevant to the existing stage contract, including:

- status and gate outcome;
- required output fields and their validated values/types;
- required decision, next action, or remediation action;
- identified blockers, failures, and ordered reasons where order is contract-significant;
- required artifacts or conclusions;
- absence of contradictory instruction, conclusion, or action; and
- absence of any omitted required conclusion.

Applicable lifecycle-consumed metadata, classifications, task identities, allowed paths, verification commands, result validation, blocking state, authority-conflict conclusions, routing, and output-write behavior MUST also be compared when the existing stage contract consumes them. Any lifecycle-significant difference not explicitly permitted by existing authority is a semantic regression.

Free-form provider narrative need not be text-identical unless it is an authoritative or deterministic required artifact. Each stochastic result MUST independently satisfy the existing result, output, gate, and lifecycle contract. Narrative wording alone cannot determine PASS or FAIL, and live results cannot replace deterministic semantic tests.

When deterministic comparison cannot resolve required meaning, a bounded human or separately explicitly approved rubric review may assess only the unresolved contract-relevant proposition and MUST record the proposition, evidence class, reviewer/tooling, and decision. LLM-only subjective grading is never sole PASS evidence.

## 8. Lifecycle and gate comparison

For each applicable pair, evaluation MUST compare:

- lifecycle transitions and lifecycle-significant side effects;
- stage terminal status;
- gate result and the meaning/availability of `INCOMPLETE` where applicable;
- provider and subprocess call cardinality;
- optimization applicability, pre-dispatch fallback, shared-prerequisite propagation, and post-dispatch failure behavior; and
- controller routing, output writes, persistence, checkpoints, and recording where the existing lifecycle consumes them.

The optimized candidate is atomic and cannot be partially dispatched. Optimization-specific pre-dispatch failure permits zero optimized calls and at most one fresh `BASELINE` dispatch. Shared-prerequisite failure propagates under existing semantics. Provider or parse failure after dispatch permits no `BASELINE` retry. Provider/subprocess calls MUST NOT exceed one per logical execution.

No new lifecycle state or gate result is created. Passing requires:

```text
lifecycle_regression_count = 0
gate_regression_count = 0
```

## 9. PASS, FAIL, and INCOMPLETE

The only evaluation statuses are `PASS`, `FAIL`, and `INCOMPLETE`.

`PASS` requires every applicable condition below:

- `authority_coverage == 100%`;
- `authority_byte_mismatch_count == 0`;
- `reconstruction_exact_match == true` wherever reconstruction is exercised;
- `semantic_regression_count == 0`;
- `lifecycle_regression_count == 0`;
- `gate_regression_count == 0`;
- every executed mandatory controlled-corpus case has its expected deterministic outcome; and
- the full regression suite passes when implementation closure later occurs.

Efficiency metrics may be recorded as bounded factual measurements but are not safety PASS substitutes. Provider savings are not required for M4.2 PASS because the current provider boundary does not support reuse.

`FAIL` means an executed mandatory criterion has a negative outcome. This includes an authority, reconstruction, semantic, lifecycle, gate, fallback, call-cardinality, determinism, default-compatibility, evidence-discipline, or implementation-attributable regression failure. When both missing evidence and a demonstrated mandatory failure exist, `FAIL` wins.

`INCOMPLETE` means required evidence is unavailable, a mandatory current case was not executed, or required attribution is unresolved without an observed mandatory failure. If a provider-token claim is evaluated, absence of Blocker 9 valid evidence makes that metric/claim `INCOMPLETE`. Provider-token evidence absence alone does not fail or make the M4.2 safety evaluation incomplete when no provider-token savings claim is made.

## 10. Evidence location and format

Future M4.2 implementation closure MUST place its bounded, committed, human-readable evaluation evidence at:

```text
docs/context/m4.2-evaluation-report.md
```

The report MUST NOT be created by this planning decision. It is documentation evidence, not runtime persistence, telemetry, lifecycle authority, or implementation authority. Machine-generated data remains ephemeral, in memory, or evaluation/test-local and is cleaned after use unless Blocker 10 separately authorizes persistence. No machine-readable repository evidence schema or telemetry change is authorized.

The future report MUST contain safe aggregate evidence only and include:

- commit/HEAD evaluated;
- evaluation date and tooling;
- canonicalization ID and applicable comparison configuration;
- controlled corpus case names, expected outcomes, actual outcomes, and `PASS`, `FAIL`, or `INCOMPLETE` per case;
- the complete applicable measurement table from Section 3;
- authority coverage, structural counts, and byte-mismatch results;
- reconstruction count and exact-match results;
- semantic, lifecycle, and gate regression results;
- fallback and provider/subprocess call-cardinality results where applicable;
- the Blocker 6 provider-boundary limitation;
- Blocker 9 provider-usage validity status and actual usage with valid provenance, or `unavailable`;
- focused and full test results when implementation exists;
- final `PASS`, `FAIL`, or `INCOMPLETE` decision; and
- known limitations, including non-executable future placeholders.

The report MUST NOT contain raw component or authority bodies, prompts, provider payloads, provider transcripts or responses, stdout/stderr, source histories, secrets or secret-derived measurements, environment dumps, arbitrary exception text, or unsanitized absolute paths. Evidence SHOULD use non-sensitive counts, digests for permitted non-secret content, closed enums/statuses, typed failure categories, and sanitized repository-relative paths.

## 11. Blocker boundaries and no-claim rule

Blocker 9 remains explicitly unresolved. Actual provider-token claims require Blocker 9 valid usage evidence. Codex CLI `tokens used`, byte counts, tokenizer estimates, and other estimates are not provider-token evidence. Without valid usage, the metric is `unavailable` and any evaluated provider-token claim is `INCOMPLETE`; no value may be fabricated, estimated, or interpreted as zero.

Blocker 10 remains explicitly unresolved. Planning and evaluation data may remain ephemeral or in memory. The human-readable report authorized in Section 10 is documentation evidence only and does not authorize persistent machine evaluation metadata, runtime persistence, `.sdd` state, or telemetry fields/events.

This contract makes no provider-savings, token-savings, byte-savings, cache-savings, or percentage-optimization claim.

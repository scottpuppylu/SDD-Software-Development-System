# M4.3 Runtime Git Policy Viability v1

## 1. Scope

This Round 2 review is limited to the value semantics and policy viability of `GIT_STATUS` and `CURRENT_BRANCH` for Stage 08. It assumes, only for planning evaluation, that a future approved provenance mechanism could prove `TRUSTED_INTERNAL_RUNTIME`. It does not implement provenance, promote either component without complete evidence, or authorize production code, tests, or a commit.

The reviewed evidence is limited to the authorized runtime Git evidence, provenance-boundary semantic result, Stage 08 declaration and execution contract, the two runtime-input producer branches, `_git()` normalization and failure behavior, and Stage 08 instructions only where they describe these values semantically.

## 2. Frozen provenance assumption

For this evaluation, explicit structural provenance originating at the authorized internal producer and preserved to compiler classification may establish `TRUSTED_INTERNAL_RUNTIME`. Caller-supplied, missing, malformed, lost, ambiguous, or otherwise unproven provenance remains `UNTRUSTED_OR_UNPROVEN_RUNTIME` and must remain exact. Trust is not inferred from content, key name, stage mapping, source role, or compiler coordinate.

All other frozen rules remain unchanged: authority coverage is 100%; authority byte mismatch is 0; `UNKNOWN`, unproven provenance, `MIXED_AUTHORITY`, and governance remain exact; task identity remains absent; `BASELINE` remains the default and `OPTIMIZED` an explicit attempt only; no partial optimized dispatch or post-dispatch retry is allowed; provider/subprocess calls remain capped at one; telemetry remains schema 1.0.4; persistence and provider-side reuse remain unauthorized; the provider boundary remains `SELF_CONTAINED_FULL_INPUT`; and token-budget truncation, semantic summarization, and semantic ranking remain prohibited. `GIT_HISTORY` remains the only currently reducible component.

## 3. GIT_STATUS semantic analysis

The internal producer runs `git status --porcelain=v1` and returns successful stdout after outer `.strip()`. An empty string is therefore a possible successful producer value. A nonzero command result raises instead of supplying a value. The producer does not validate a closed line grammar.

Stage 08 declares `GIT_STATUS` as a required runtime input. Its resume protocol separately requires `Inspect git status`; its checkpoint preconditions include `SCOPE_RESPECTED` and `UNEXPECTED_DIFF_REVIEWED`. These requirements give the status observation positive operational meaning. The authority does not state that an absent component means the status was checked and found clean.

### A1. `OMIT_WHEN_CLEAN`

This shape is not semantically proven. A present empty value can represent successful execution of the required status command followed by the producer's specified normalization. Absence instead establishes no status observation in the inspected request contract. Stage 08 needs to perform or receive evidence for the required inspection, so absence cannot be treated as unambiguously equivalent to checked-and-clean. The fact that the value is empty does not make the component semantically empty.

### A2. `BOUNDED_STATUS_LINES`

This shape is not semantically proven. Stage 08 must respect scope and review unexpected diffs. Any omitted status entry could identify a changed path relevant to either obligation. No inspected authority permits discarding entries, defines an irrelevant class of paths, or provides a deterministic safe bound. Selecting entries would require an unauthorized inference about relevance, while a purely positional bound could hide material entries.

### A3. `NORMALIZED_STATUS_SUMMARY`

This shape is unsafe and unauthorized. No repository authority defines an exact summary equivalent to the complete value. Counts, categories, path selection, or other summaries would lose status evidence and introduce semantic summarization.

## 4. GIT_STATUS policy viability

No evaluated policy has a proof that its provider-bound result is semantically equivalent for Stage 08. `OMIT_WHEN_CLEAN` conflates successful clean inspection with absence; bounded lines can conceal a relevant changed path; and summaries are prohibited. Ambiguity must fail closed to exact, leaving no useful eligible case.

Accordingly, `GIT_STATUS_POLICY_VIABLE = NO`, no policy ID is defined, and the component remains `INSUFFICIENT_EVIDENCE`.

## 5. CURRENT_BRANCH semantic analysis

The internal producer runs `git branch --show-current` and returns successful stdout after outer `.strip()`. Empty output is possible through this producer path, but the repository authority does not define its meaning or establish detached-HEAD behavior. A nonzero command result raises instead of supplying a value. The producer does not validate a closed single-line branch-name grammar.

Stage 08 declares `CURRENT_BRANCH` as a required runtime input and its resume protocol requires `Identify branch`. This gives exact branch identity positive operational relevance. The inspected Stage 08 request contract contains no other component guaranteed to carry exactly the same branch identity for every eligible request.

### B1. `OMIT_IF_STAGE_METADATA_OR_OTHER_CONTEXT_ALREADY_PROVES_BRANCH`

This shape is not available. Stage metadata identifies the stage, not the current Git branch. No other exact trusted component in the authorized Stage 08 inputs is established as a duplicate of `CURRENT_BRANCH`, and no structural invariant guarantees such duplication for every eligible request. Omission would therefore remove the only declared branch-identity value rather than eliminate proven redundancy.

### B2. `OMIT_EMPTY`

This shape is not semantically proven. The repository establishes that normalization may produce an empty string but does not define what that value means. In particular, detached-HEAD behavior must not be inferred. Absence also does not prove that the required branch-identification command ran and produced empty output. Present-empty and not supplied are therefore not interchangeable.

### B3. `REDUCE_BRANCH_STRING`

This shape is unsafe and unauthorized. No exact deterministic equivalence permits hashing, truncating, summarizing, or further normalizing a branch name while preserving the exact identity Stage 08 is required to identify.

## 6. CURRENT_BRANCH policy viability

No evaluated policy has closed use semantics or an exact semantic-equivalence proof. Exact redundancy is not structurally established, empty-value meaning is undefined, absence is not equivalent to present-empty, and branch-string reduction loses identity. Ambiguity must fail closed to exact, leaving no useful eligible case.

Accordingly, `CURRENT_BRANCH_POLICY_VIABLE = NO`, no policy ID is defined, and the component remains `INSUFFICIENT_EVIDENCE`.

## 7. Usefulness assessment

The assumed provenance boundary would satisfy the trusted-origin prerequisite for a future controlled case, and both components are non-authority and non-governance. Neither component passes the remaining usefulness gate, however:

- No omission or reduction condition is proven semantically equivalent for Stage 08.
- The empty cases cannot safely substitute absence for present-empty.
- No bounded `GIT_STATUS` subset is proven complete for Stage 08's scope and unexpected-diff obligations.
- No exact duplicate of `CURRENT_BRANCH` is guaranteed in the same request.
- No non-zero practical reduction case survives the semantic-safety gate.
- With no safe transformation, implementation complexity cannot be justified.

Although removing any serialized component could mechanically remove provider-bound bytes, that observation is not a valid reduction proof when the omission changes or leaves unresolved the request semantics. A trivial theoretical byte saving does not pass the usefulness gate.

## 8. Controlled evaluation requirements

No component is promoted, so no candidate-specific controlled evaluation contract is authorized. Any future evidence round seeking promotion would first need to close the relevant content and use semantics and define one exact named policy. A later, separately approved evaluation would then have to cover, at minimum:

- an eligible trusted value and an ineligible trusted value;
- caller-supplied or otherwise unproven provenance, preserved exact;
- empty values and malformed or ambiguous values, preserved exact unless equivalence is separately proven;
- `BASELINE` versus `OPTIMIZED` semantic equality;
- authority coverage of 100% and authority byte mismatch of 0;
- zero semantic, lifecycle, and gate regressions;
- no more than one provider/subprocess call and no post-dispatch retry;
- direct observation of complete provider-bound request bytes; and
- a passing full suite.

No provider-token claim may be made unless valid structured schema-1.0.4 usage exists. These are requirements for a possible future evaluation, not authorization to add tests or implement a candidate now.

## 9. Authorization boundary

This document is evidence and policy-viability analysis only. It does not authorize provenance implementation, production changes, tests, public API changes, lifecycle changes, telemetry changes, persistence, provider cache or reuse, task identity, automatic context budgeting, authority summarization, semantic retrieval or ranking, or candidate implementation. It creates no named policy. Implementation remains separately blocked pending project approval.

# M4.2 Stage and Task Semantics v1

## 1. Status and scope

This document is planning authority input for M4.2 Blocker 2 only. It does not authorize M4.2 implementation, context omission, context reduction, or changes to production code or tests. Blockers 3-10 remain outside this decision.

Sources inspected were limited to Section 16 of `docs/context/context-optimization-plan-v1.md`, Sections 7-10 of `docs/context/m4.2-component-inventory-v1.md`, `.sdd/stages.yaml`, `StageRunner.build_request()` and its required runtime-input collection and narrow stage-specific artifact conditionals, and the `StageExecutionRequest` definition.

## 2. Stage identity

`.sdd/stages.yaml` is the current authoritative source for stage identity and stage declarations. The mapping keys under `stages` are the stage IDs, and each stage declaration supplies its stage metadata and contract.

The following boundaries apply:

- **Authoritative stage definition:** the declaration keyed by stage ID in `.sdd/stages.yaml`.
- **Runtime request representation:** `StageExecutionRequest.stage_id`, `stage_name`, `stage_type`, `core_question`, and `contract` represent the selected declaration at execution time. `StageRunner.build_request()` obtains the declaration and constructs this request; the request is not an independent stage-definition authority.
- **Observed component-to-stage association:** content placed in `artifacts`, `semantic_inputs`, or `runtime_inputs` by current producer behavior is an observed association. It is not omission authority merely because it appears only for a particular stage.
- **Future M4.2 selection authority:** for components directly named by a stage's declaration, that declaration may establish stage-required candidate relevance. It does not establish that any component is safe to omit, reduce, summarize, or replace.

## 3. Stage mapping semantics

`.sdd/stages.yaml` actually encodes the following for the current stages:

| Property | Encoding |
|---|---|
| Stage ID | The key under `stages`, `"01"` through `"10"`. |
| Stage name | `name` in every stage declaration. |
| Stage type | `type` in every stage declaration. |
| Core question | `core_question` in every stage declaration. |
| Required file inputs | `required_inputs.files`; every stage has a list, including an empty list for Stage 01. |
| Required semantic inputs | `required_inputs.semantic` where declared. It is declared for Stages 01-07 and 10 and absent for Stages 08-09. Absence records no declared required semantic inputs; it does not prove that other supplied context is omittable. |
| Required runtime inputs | `required_inputs.runtime` where declared. It is declared for Stages 08-09 and absent for Stages 01-07 and 10. Absence records no declared required runtime inputs; it does not prove that producer-supplied runtime context is omittable. |
| Outputs | `outputs` in every stage declaration. Stages 01-07 and 09-10 declare file outputs; Stage 08 declares evidence outputs. |

These declarations are sufficient planning authority for M4.2 to use directly declared required inputs as the source of `STAGE_REQUIRED_CANDIDATE` eligibility.

**Exact boundary:** stage declaration establishes candidate relevance only; it does not by itself authorize omission of authority-bearing or fail-closed context.

This authorization does not retroactively reclassify the Blocker 1 inventory and is not implementation authority. Any future classification must preserve the conservative constraints in Section 6.

## 4. StageRunner conditionals

`StageRunner.build_request()` currently produces stage-specific components not directly declared as required inputs in `.sdd/stages.yaml`:

- Stages 02-06 may receive their existing output artifact during an authoring-stage rerun.
- Stage 09 may receive `.sdd/state/post-implementation-verification.md` and `.sdd/state/implementation-state.md` as supplemental artifacts when present.
- Stage 10 may receive a bounded set of release-relevant supplemental artifacts.
- Stage 10 runtime collection adds `RELEASE_GIT_IDENTITY` and `STAGE10_CONTEXT_POLICY`, although neither key is declared under `required_inputs.runtime` for Stage 10.

These conditionals are **current producer behavior only**, not authoritative stage mapping. The code comments characterize the Stage 09 and Stage 10 artifact packets as supplemental, and the Stage 10 collector characterizes its artifacts as evidence rather than authority. The Stage 02-06 behavior supports read-modify-write reruns but does not amend the YAML declarations.

M4.2 may observe these associations but may not use them as selection or omission authority under this Blocker 2 decision. Separate explicit planning authority is required before any such producer-only conditional can establish selection eligibility.

Runtime collection also translates the declared `RECENT_COMMITS` or `GIT_HISTORY` request into the produced `GIT_HISTORY` request key. That is current producer representation behavior; it does not create a new authoritative stage declaration.

## 5. Existing task identity semantics

`StageExecutionRequest` contains exactly these fields: `stage_id`, `stage_name`, `stage_type`, `core_question`, `contract`, `artifacts`, `semantic_inputs`, `runtime_inputs`, and `stage_instructions`. It contains no explicit current execution task identity.

The following are distinct and must not be promoted into task identity:

- `tasks.md` is an artifact containing execution decomposition authority; its presence or text is not a request task coordinate.
- Convergence task structures appear on `StageExecutionResult`, not as explicit current-task identity on `StageExecutionRequest`.
- Stage ID, stage name, stage type, and core question identify the stage, not a task.
- Task text, task list order, semantic values, runtime values, and convergence task data do not become task identity through inference.

Therefore task-aware selection is unavailable. `TASK_REQUIRED_CANDIDATE` eligibility is not authorized for planning unless a separately authorized request semantic later supplies explicit task identity.

## 6. Conservative semantics carried forward

- Authority coverage must remain 100%.
- Exact authority boundaries remain Blocker 3.
- Stable identities remain Blocker 4.
- Baseline/delta semantics remain Blocker 5.
- No omission or reduction is authorized here.
- `UNKNOWN` and `MIXED_AUTHORITY` remain fail closed.
- Task-aware selection remains unavailable because explicit task identity is absent.
- Observed association, producer behavior, and runtime request presence do not independently authorize omission.

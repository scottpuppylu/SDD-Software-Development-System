# M4.2 Authority Equivalence v1

**Status:** Planning authority input only

## 1. Scope and authority boundary

This document resolves M4.2 Blocker 3 for planning only. It defines authority coverage and byte-equivalence boundaries. It does not authorize M4.2 implementation, production-code changes, test changes, omission, reduction, reuse, cache behavior, provider behavior, persistence, or telemetry-schema changes. Blockers 4-10 remain outside this decision, and M4.2 implementation remains blocked.

Authority remains domain-specific. Product Requirement authority remains the PRD, Technical Contract authority remains the Spec, and Implementation Decision authority remains the Design. Tasks cannot override authoritative artifacts. This document creates no linear authority precedence and does not resolve authority conflicts.

## 2. Authority-set boundary

For one logical request, the **source authority set** is the complete set of source components at the existing request/component assembly boundary whose existing classification or treatment is any of:

- `KNOWN_AUTHORITY`;
- `KNOWN_GOVERNANCE`;
- `MIXED_AUTHORITY`;
- `UNKNOWN` where existing fail-closed exact treatment applies; or
- otherwise `EXACT_REQUIRED` under an already approved closed classification or treatment rule.

The term **authority-protected component** denotes any member of that set. It is a protection/equivalence term; it does not promote governance, unknown content, or compiled context into lifecycle or domain authority.

Existing closed authority classification, artifact-role mapping, component boundaries, absent-versus-present treatment, and canonicalization authority remain unchanged. Unmapped or ambiguous content remains `UNKNOWN` or conservatively `MIXED_AUTHORITY` and exact-required. No content inspection, stage relevance, selector result, telemetry label, filename resemblance, or implementation intuition may remove a component from the source authority set.

The **selected/reconstructed effective authority set** is the set of authority-protected component occurrences actually represented in the effective provider input after selection or baseline-plus-delta reconstruction, evaluated at those same existing component boundaries. A substitute with similar meaning, a summary, or content taken from a different component is not the source component.

## 3. Authority coverage

Authority coverage is a structural, deterministic one-to-one coverage test, separate from byte equality. For each source authority component, the effective provider input must contain exactly one corresponding occurrence at its stable/current component coordinate and, where provider-input ordering affects the effective input, at the same ordered position required by fresh exact assembly.

A component is **present for coverage** only when that one-to-one coordinate and required-position correspondence is unambiguous. Byte equality is tested separately under Section 4.

The following prevent a claim of 100% coverage:

- a **missing authority component**: no corresponding effective occurrence;
- an **extra substitute component**: other content is offered in place of the required source component;
- a **duplicate authority component**: more than one effective occurrence corresponds or may correspond to one source component;
- a **reordered authority component**: its position differs where ordering affects effective provider input; or
- failure to include any **exact required component** covered by Section 2.

For a request with a non-empty required set:

```text
authority_coverage =
  authority_present_component_count / authority_required_component_count * 100%
```

The value is 100% only if the mapping is a total bijection, every required position is satisfied, and there is no missing, substitute, duplicate, extra mapped occurrence, ordering ambiguity, or other mapping ambiguity. For an empty required set, coverage is 100% only when the effective set is also empty and no ambiguity or anomalous occurrence exists. Counts are exact integers; evaluation may retain the ratio rather than use rounded arithmetic. Rounding must never produce 100%.

Coverage does not authorize summarization, transformation, or semantic substitution.

## 4. Exact byte-equivalence boundary

`authority byte mismatch = 0` means that every authority-protected source component has exactly the same canonical UTF-8 byte sequence as its single corresponding component extracted from the effective selected/reconstructed provider input representation.

Comparison is:

- per authority-protected component;
- at the existing component boundary;
- by the stable identity when Blocker 4 later defines it, and until then by the unambiguous current component coordinate already established by existing contracts;
- over exact canonical UTF-8 bytes under the already frozen canonicalization ID and rules; and
- over the ordered component sequence as fresh exact assembly produces it wherever order affects effective provider input.

This document does not create a canonicalization algorithm, identity namespace, digest rule, collision rule, or stable identity construction. Those identity details remain Blocker 4. Digest equality alone is not byte equivalence. Any transformed, normalized, summarized, truncated, semantically equivalent, or otherwise substituted authority content is a mismatch unless the already frozen canonicalization itself produces the compared canonical bytes.

The effective provider-input comparison is not satisfied merely by finding matching bytes elsewhere in a payload. The bytes must belong to the corresponding component occurrence and required ordered position. In addition to all per-component byte comparisons, the ordered authority-protected component projection of effective reconstructed provider input must equal the corresponding projection of fresh exact assembly.

## 5. Selection is not equivalence or omission authority

`STAGE_REQUIRED_CANDIDATE` eligibility from the Blocker 2 decision establishes candidate relevance only. It is neither an authority-equivalence proof nor omission authorization.

A stage mapping, observed producer association, runtime presence, selector decision, or relevance classification is insufficient by itself to omit an authority-bearing, `UNKNOWN`, `MIXED_AUTHORITY`, governance, or otherwise exact-required component. Omission requires separate later authority and all required contracts; none is granted here. Blocker 3 equivalence proves only whether an attempted effective representation preserves the protected source set exactly.

## 6. Fail-closed behavior

Each of the following invalidates optimized omission or reuse for the affected context:

- missing authority component;
- duplicate authority component;
- ambiguous source-to-effective mapping;
- unavailable component identity or coordinate;
- source/effective canonical-byte mismatch;
- ordering mismatch or ambiguity where ordering affects effective provider input;
- transformed authority content; or
- authority conflict.

The required planning behavior is fail closed to fresh exact assembly and exact inclusion for the affected context. An authority conflict continues to block the affected implementation; fallback does not resolve the conflict. This document defines the required outcome only, not runtime fallback mechanics, dispatch behavior, or provider-call behavior.

## 7. Baseline-plus-delta equivalence boundary

For any future baseline-plus-delta path, the effective reconstructed provider input must contain authority content exactly equivalent to fresh exact assembly under Sections 2-4. Reconstruction must preserve the complete protected set, one-to-one component correspondence, exact canonical UTF-8 bytes, and required effective ordering.

This invariant does not define a delta format, baseline lifetime, cache key, provider reuse mechanism, or any other Blocker 4-10 contract.

## 8. Required evaluation-local metrics and invariants

These definitions are planning metrics. They may remain evaluation-local or in-memory and do not amend telemetry schema 1.0.4.

- `authority_source_component_count`: exact integer cardinality of the source authority set for the logical request.
- `authority_required_component_count`: exact integer count of source components to which the Section 2 exact-equivalence requirement applies. Under the classifications frozen here, this equals `authority_source_component_count`.
- `authority_present_component_count`: exact integer count of required source components having exactly one unambiguous corresponding effective occurrence at the required coordinate and ordered position. Byte equality is not included in this structural count.
- `authority_missing_component_count`: exact integer count of required source components having no corresponding effective occurrence at the required coordinate and ordered position.
- `authority_duplicate_component_count`: exact integer count of required source components for which more than one effective occurrence corresponds or may correspond.
- `authority_byte_mismatch_count`: exact integer count of present, uniquely mapped required components whose source and effective canonical UTF-8 byte sequences differ. Missing or duplicate components remain recorded by their structural counts and independently fail equivalence rather than being relabeled as byte mismatches.
- `authority_coverage`: the exact ratio defined in Section 3, reported as 100% only when all of its bijection, ordering, and ambiguity conditions hold.

Extra substitutes, ordering failures, and mapping ambiguities are deterministic validation failures even though this document does not add separate required metric names for them. The required invariants are `authority_coverage = 100%` and `authority_byte_mismatch_count = 0`; both must hold, and neither can compensate for failure of the other.

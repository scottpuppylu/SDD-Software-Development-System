# M4.3 Release Git Identity Viability v1

## 1. Scope

This Round 3 document evaluates only `runtime_inputs["RELEASE_GIT_IDENTITY"]` for evidence and policy viability. It uses only the authorized operational-plan classification and boundary, the applicable provenance rule, the Stage 10 declaration and instruction, and the runtime producer plus `_git()` behavior.

This is not an implementation authorization. It does not analyze or change `GIT_STATUS`, `CURRENT_BRANCH`, `BUILD_LINT_TYPECHECK_EVIDENCE_IF_APPLICABLE`, `SOURCE_CODE`, `TEST_EVIDENCE`, `STAGE10_CONTEXT_POLICY`, or `GIT_HISTORY` policy internals.

## 2. Frozen assumptions

- Authority coverage remains 100%, and authority byte mismatch remains 0.
- `UNKNOWN`, unproven provenance, `MIXED_AUTHORITY`, and governance remain exact.
- Task identity remains absent.
- `BASELINE` remains the default. `OPTIMIZED` remains an explicit attempt only.
- Provider/subprocess calls are capped at one, with no post-dispatch retry and no partial optimized dispatch.
- Telemetry schema remains 1.0.4.
- Persistence and provider-side reuse remain `NOT_AUTHORIZED`.
- The provider boundary remains `SELF_CONTAINED_FULL_INPUT`.
- Token-budget truncation and semantic summarization/ranking remain prohibited.
- `GIT_HISTORY` remains the only `CURRENTLY_REDUCIBLE` component.
- The planning provenance assumption permits policy analysis as if a future, separately approved mechanism could prove `TRUSTED_INTERNAL_RUNTIME`; it does not authorize that mechanism.

## 3. Producer and field inventory

For Stage 10, `StageRunner._collect_runtime_inputs()` unconditionally constructs a six-field mapping at `RELEASE_GIT_IDENTITY`. Five fields call `_git(..., allow_failure=True)`. `_git()` executes `git` in the repository root, decodes stdout as UTF-8 with replacement for decoding errors, returns the whole stdout after `.strip()`, and returns `""` on any nonzero exit when failure is allowed. Consequently, each Git-produced field is always a string; its empty value can mean either empty stripped stdout or command failure. The producer records no success/failure discriminator.

The Stage 10 YAML has no runtime `required_inputs` declaration for `RELEASE_GIT_IDENTITY`; it requires semantic `RELEASE_IDENTITY` and checks `VERSION`, `BRANCH`, `COMMIT_OR_TAG`, `TARGET_ENVIRONMENT`, and `DEPLOYMENT_TARGET`. The Stage 10 instruction says to review release identity but does not define consumption of these six Git fields. Producer association therefore does not establish omission authority or a field reconstruction rule.

## 4. Provenance result

`RELEASE_GIT_IDENTITY_PROVENANCE = MIXED_OR_UNPROVEN`.

The producer creates this mapping internally, but the compiler boundary receives a plain caller-accessible runtime-input mapping. The applicable provenance evidence establishes that arbitrary caller-supplied values can occupy the same key and that no structural provenance discriminator survives to classification. Key name, Stage 10 association, content match, source role, and compiler coordinate cannot establish origin.

Therefore the current value must remain exact. Policy viability may still be considered under the expressly limited planning assumption that a future approved mechanism could prove `TRUSTED_INTERNAL_RUNTIME`. Missing, malformed, lost, ambiguous, caller-supplied, or otherwise unproven provenance must fail closed to byte-exact treatment.

## 5. Field-level semantic analysis

### 5.1 `semantics`

The fixed text is not proved to be redundant governance text. Its second sentence supplies a specific interpretation: dirty-tree state is evidence to assess, not an automatic release decision. Neither the Stage 10 declaration nor its instruction supplies that exact interpretation, and the operational plan already identifies unproved release semantics as a blocker. Omission therefore lacks structural proof that Stage 10 receives the same rule elsewhere. Rejected.

### 5.2 `recent_commits`

The field is not proved redundant with any other required Stage 10 input. Its producer already makes an intentional deterministic selection of 10 log entries. No authorized evidence proves that a smaller count, a field projection, or omission preserves Stage 10's release assessment. The separate `GIT_HISTORY` policy supplies no authorization for this field and is not reused. Rejected.

### 5.3 `working_tree_status`

Present-empty cannot safely become absent on current evidence. Although the producer already collapses an empty successful result and command failure to the same empty string, no Stage 10 consumption contract proves that mapping absence has the same meaning as a present empty field. The mapping's semantics also establishes that dirty-tree evidence is to be assessed. Any subset of a nonempty status could omit relevant evidence, and completeness requirements are not closed by the Stage 10 declaration. Rejected.

### 5.4 `branch`

Stage 10 explicitly checks `BRANCH`. No other inspected field is proved to duplicate exact branch identity, and the repository defines no normalization equivalence. Omission, rewriting, or normalization could alter the release identity assessed by Stage 10. Rejected.

### 5.5 `head_commit`

Stage 10 explicitly checks `COMMIT_OR_TAG`. No exact duplicate of `head_commit` is structurally proved. In particular, the producer does not define an equivalence between `rev-parse HEAD` output and any substring or line of another field. Shortening or truncating the value is forbidden because exact equivalence is not proved. Rejected.

### 5.6 `head_tags`

Stage 10 explicitly checks `COMMIT_OR_TAG`. Empty output may result from empty stripped stdout or allowed command failure, and there is no contract equating either with an absent mapping field. Nonempty output may be multiline; complete tags are potentially part of the release identity, and no deterministic bounded subset is proved sufficient. Rejected.

## 6. Policy viability

No field-level policy survives the semantic-equivalence gate. Consequently, no policy ID is defined.

Even under assumed `TRUSTED_INTERNAL_RUNTIME`, every proposed transformation fails at least one necessary condition:

- exact branch and commit-or-tag fields have explicit Stage 10 relevance and no proved duplicate;
- status and recent history lack an authoritative safe omission or smaller-selection rule;
- empty-to-absent transformations lack a mapping-consumption equivalence contract;
- the fixed semantics text contains a unique, evidenced interpretation rule rather than proved redundancy.

All ambiguity therefore fails closed to exact.

## 7. Usefulness assessment

No non-zero practical provider-bound reduction is proved semantically safe. Removing a fixed field name, an empty string, or a small fixed literal would decrease serialized bytes in some representation, but byte decrease alone does not establish semantic equivalence, and trivial or merely theoretical savings do not pass the usefulness gate. No qualifying policy exists whose benefit can justify implementation complexity.

`PROVIDER_BOUND_REDUCTION_PROVEN = NO` because no named controlled case survives all gates.

## 8. Controlled evaluation requirements

There is no promoted policy, so no policy-specific future controlled cases are defined by this document. Any later proposal would require separate approval and must, at minimum, cover an eligible trusted value, an ineligible trusted value, unproven/caller provenance, an empty value, and any applicable malformed or ambiguous value. It would also have to demonstrate:

- `BASELINE` versus `OPTIMIZED` semantic equality;
- authority coverage of 100% and authority byte mismatch of 0;
- zero semantic, lifecycle, and gate regressions;
- no more than one provider/subprocess call;
- directly observed provider-bound bytes;
- full-suite PASS; and
- no provider-token claim unless schema-1.0.4 structured provider usage is valid and attributable.

These are conditions for a future separately authorized proposal, not authorization to implement or test one now.

## 9. Authorization boundary

This document does not authorize provenance implementation, production changes, tests, public API changes, lifecycle changes, telemetry changes, persistence, provider cache/reuse, task identity, automatic context budgeting, authority summarization, semantic retrieval/ranking, or candidate implementation.

`RELEASE_GIT_IDENTITY` remains `INSUFFICIENT_EVIDENCE`. M4.3 implementation remains blocked pending separate project approval. The unresolved blockers are a structural trusted-provenance mechanism and, independently for every field, an authoritative Stage 10 semantic-equivalence rule yielding useful practical reduction. This round proves neither.

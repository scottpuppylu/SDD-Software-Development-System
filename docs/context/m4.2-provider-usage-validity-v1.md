# M4.2 Blocker 9: Provider-Usage Validity Audit

Status: planning authority input only. This document does not authorize M4.2 implementation and does not decide Blocker 10 persistence.

## 1. Provider usage evidence model

Schema `1.0.4` represents provider usage in the required `MeasurementEvent.usage` field. A `provider_call` carries a `Usage` object; event types that do not carry provider usage use `usage: null`, which is neither unavailable usage nor zero.

The exact `Usage` fields are:

| Field | Repository type/values | Meaning |
|---|---|---|
| `availability` | `available` or `unavailable` | State of the provider usage observation. |
| `quality` | `actual` or `unavailable` | Whether the observation is actual provider usage or unavailable. |
| `usage_source` | `openai_responses_usage`, `openai_responses_unavailable`, or `codex_cli_unavailable` | Usage provenance. |
| `input_tokens` | non-negative integer or `null` | Provider-reported aggregate input tokens when valid. |
| `output_tokens` | non-negative integer or `null` | Provider-reported aggregate output tokens when valid. |
| `total_tokens` | non-negative integer or `null` | Provider-reported aggregate total tokens when valid. |
| `component_tokens` | closed object or `null` | For available usage, an object with exactly `cached_input_tokens` and `reasoning_output_tokens`; for unavailable usage, `null`. Each component member is a non-negative integer or `null`. |

`0` is a valid observed numeric zero. Boolean, negative, malformed, and non-integer values are not actual token observations.

## 2. Valid actual usage rule

Actual provider evidence is valid only when all applicable repository conditions hold:

1. A `Usage` object exists and its model validation succeeds.
2. `availability` is `available`.
3. `quality` is `actual`.
4. `usage_source` is `openai_responses_usage`.
5. The measurement provider identity is compatible with that provenance. `measure_provider_call()` permits `openai_responses_usage` only for provider `openai`; provider `codex` permits only `codex_cli_unavailable`.
6. Every non-null aggregate and component count is an integer, is not a boolean, and is at least zero.
7. `component_tokens` is an object containing exactly `cached_input_tokens` and `reasoning_output_tokens`.
8. Values treated as actual are provider-reported; estimates and derived values are excluded.

Schema 1.0.4 explicitly permits individual aggregate fields to be `null`. Current OpenAI conversion requires at least one valid aggregate among `input_tokens`, `output_tokens`, and `total_tokens` before it constructs available usage. Thus the current repository does **not** require both input and output counts to be non-null to represent available actual usage. It also defines no arithmetic consistency validation requiring `total_tokens` to equal `input_tokens + output_tokens`; no such rule may be added by this audit.

For direct `Usage` construction, a malformed non-null numeric value fails model validation. In the OpenAI response adapter, malformed or absent individual provider fields are normalized to `null`; if all three aggregate fields normalize to `null`, no `Usage` object is produced and the measurement becomes unavailable.

## 3. OpenAI Responses path

`_openai_response_usage(payload)` reads the response object at `payload["usage"]` and maps:

| Provider response field | Internal field |
|---|---|
| `usage.input_tokens` | `input_tokens` |
| `usage.output_tokens` | `output_tokens` |
| `usage.total_tokens` | `total_tokens` |
| `usage.input_tokens_details.cached_tokens` | `component_tokens.cached_input_tokens` |
| `usage.output_tokens_details.reasoning_tokens` | `component_tokens.reasoning_output_tokens` |

The adapter accepts only non-boolean integers greater than or equal to zero. Invalid or absent individual values become `null`. It returns `None` when the payload is not an object, `usage` is not an object, or all three aggregate fields are invalid/absent. Otherwise it constructs `Usage(availability=available, quality=actual, usage_source=openai_responses_usage, ...)`, with both canonical component members present.

`OpenAIResponsesExecutor` initializes `provider_usage = None`, parses the JSON response, calls `_openai_response_usage(payload)`, and resets `provider_usage` to `None` if conversion raises. It passes the result to `measure_provider_call()` with provider identity `openai`. If the result is `None`, `measure_provider_call()` constructs unavailable OpenAI usage with source `openai_responses_unavailable` and all token fields `null`. HTTP errors, timeouts, transport failures, absent usage, and usage without any valid aggregate therefore produce unavailable usage when the telemetry event is constructed.

When parsing succeeds as described, the resulting object satisfies schema-1.0.4 actual-usage representation and compatible OpenAI provenance.

## 4. Codex provider path

`CodexExecReasoningExecutor` calls `measure_provider_call()` with provider identity `codex` and does not pass `provider_usage`. The separately measured Codex CLI helper path in `sdd_orchestrator/codex_cli.py` does the same. Consequently, `measure_provider_call()` constructs `Usage(availability=unavailable, quality=unavailable, usage_source=codex_cli_unavailable)` with all token fields `null`.

The inspected execution paths capture subprocess stdout/stderr operationally, but they do not parse either stream into provider usage and receive no structured actual usage object. Any Codex CLI narrative `tokens used` counter is distinct from repository telemetry `provider_usage` and is not provider-token evidence.

## 6. Missing and invalid usage behavior

The following planning rules are frozen:

- Missing usage object at the provider measurement input means unavailable provider usage; `measure_provider_call()` creates the provider-specific unavailable `Usage` object.
- Incompatible provenance is invalid and `measure_provider_call()` raises validation failure.
- Malformed non-null numeric values in a constructed `Usage` object are invalid and fail model validation. The OpenAI adapter does not accept them as actual: an invalid individual field becomes `null`, and all-invalid/absent aggregates make usage unavailable.
- A provider response without reliable usage means unavailable.
- Estimate-only evidence means unavailable for provider-token claims.
- A CLI narrative/token counter means unavailable for provider-token claims.
- Unavailable usage is never converted to zero.

## 7. M4.2 evaluation consequence

A provider-token metric or claim is valid only when the evaluated provider call yields valid actual usage, schema-1.0.4 `Usage` validation succeeds, provenance is compatible with the provider identity, and the measurement belongs to that evaluated provider call. Otherwise the provider-token metric is unavailable.

For an M4.2 safety evaluation that makes no provider-token claim, unavailable provider usage does not cause safety FAIL and does not by itself make the whole safety evaluation INCOMPLETE. For an evaluated provider-token claim, unavailable valid usage makes that claim or metric INCOMPLETE.

## 8. No savings inference

This audit does not infer input-token reduction from byte reduction, token savings from local delta bytes, token savings from Codex CLI `tokens used`, token savings from tokenizer estimates, or token savings from provider call duration or cost.

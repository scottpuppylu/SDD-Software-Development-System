# M4.2 Identity Contract v1

## 1. Status and scope

This document is planning authority input for M4.2 Blocker 4 only. It is not implementation authority. It defines stable identity solely for deterministic component correspondence, unchanged-content eligibility, reconstruction validation, and deterministic evaluation.

Identity does not create authority, lifecycle state, persistence, cache authority, or omission authority. It does not alter stage or task semantics. It does not authorize omission, reduction, reuse, provider behavior, or any optimization. Existing authority classification, exact-inclusion requirements, component boundaries, and byte-equivalence requirements remain unchanged.

## 2. Namespace, version, and coordinate envelope

The frozen namespace is `sdd.context.component` and the frozen version is `m4.2-v1`.

An identity is the following ordered structural tuple:

```text
(namespace, version, stage-coordinate, task-coordinate, component-coordinate)
```

Its deterministic textual form is:

```text
sdd.context.component/m4.2-v1/<stage-coordinate>/task-absent/<component-coordinate>
```

The tuple fields and separators are part of this version's identity-coordinate grammar. Identity-coordinate canonicalization is this exact grammar plus the UTF-8 hexadecimal encoding rules below; it is not content canonicalization.

The stage coordinate is included because reuse or reconstruction across stage-specific requests must not alias. It is constructed only from the already-approved stage identity semantics:

- a present approved stage identifier is `stage-id/<encoded-stage-id>`;
- an absent approved stage identifier is `stage-absent`;
- `<encoded-stage-id>` is the original stage identifier's UTF-8 bytes encoded as lowercase hexadecimal, two digits per byte, without normalization, case folding, prefix, or separator; and
- an empty present stage identifier is `stage-id/`, distinct from `stage-absent`.

No other stage label or stage meaning may be inferred. Explicit task identity is absent in the current request model. The task field is therefore the literal `task-absent`; a task coordinate must not be parsed from artifacts, semantic inputs, runtime inputs, metadata, content, names, or execution state.

## 3. Component identity construction

The M4.1 structural component coordinates are preserved unchanged inside the M4.2 envelope:

| Component kind | `component-coordinate` |
| --- | --- |
| fixed stage contract | `request/stage-contract` |
| fixed stage instructions | `request/stage-instructions` |
| artifact keyed component | `request/artifacts/<encoded-key>` |
| semantic keyed component | `request/semantic-inputs/<encoded-key>` |
| runtime keyed component | `request/runtime-inputs/<encoded-key>` |
| stage ID metadata | `request/metadata/stage-id` |
| stage name metadata | `request/metadata/stage-name` |
| stage type metadata | `request/metadata/stage-type` |
| core-question metadata | `request/metadata/core-question` |

For every keyed component, `<encoded-key>` is the original string key's UTF-8 bytes encoded as lowercase hexadecimal, two digits per byte, without prefix or separator. There is no Unicode normalization or case folding. Non-string dictionary keys are invalid for identity construction.

The component kind and group remain explicit in the coordinate, so fixed slots, artifacts, semantic inputs, runtime inputs, and metadata cannot alias even if their keys or content match. Identity is structural: it must not incorporate or be inferred from content meaning, content digest, paths, timestamps, UUIDs, process state, locale-sensitive transformations, normalization, or case folding. This version defines no structural-identity digest.

## 4. Content canonicalization and digest

The frozen content canonicalization remains:

```text
sdd.canonical.utf8-sorted-compact-v1
```

Identity-coordinate canonicalization identifies a structural occurrence. Content canonicalization produces the canonical UTF-8 bytes of that occurrence. They are distinct operations and neither substitutes for the other.

The content digest is SHA-256 over the exact canonical content bytes, encoded as exactly 64 lowercase hexadecimal characters. It is content metadata, not component identity and not a cache key. Digest equality is only a necessary unchanged-content check. It is not proof of Blocker 3 byte equivalence, exact inclusion, ordered correspondence, or one-to-one effective occurrence; exact canonical bytes at the corresponding identity and required ordered position must still validate.

## 5. Collision and malformed identity behavior

Validation fails closed and the affected reuse or optimization is ineligible when:

- two distinct structural components produce the same identity;
- one identity is associated with different canonical content where unchanged correspondence is claimed;
- a digest-collision simulation presents equal digests but unequal canonical bytes;
- an identity has a malformed namespace, version, stage coordinate, task coordinate, component coordinate, key encoding, or tuple/text structure; or
- the namespace or version is unrecognized.

Equal digests never resolve identity ambiguity. Collision or ambiguity invalidates eligibility. This contract defines the required validation outcome only and no runtime recovery mechanics.

## 6. Deterministic ordering

Identity contains no ordinal. Structural identity is independent of incidental sequence position, while the ordered sequence is validated separately.

The existing manifest ordering remains authoritative:

1. stage contract;
2. stage instructions;
3. artifacts;
4. semantic inputs;
5. runtime inputs; and
6. metadata in the exact order `stage_id`, `stage_name`, `stage_type`, `core_question`.

Within each dictionary group, entries are sorted by the original key's UTF-8 byte sequence ascending, unsigned and lexicographic. Encoded text, locale collation, normalized or case-folded text, insertion order, and platform behavior do not determine order. Lists remain atomic within their containing component. Required effective ordering must independently equal fresh exact assembly; identity equality does not excuse reordering. No semantic ranking is defined.

## 7. Duplicate behavior

Duplicate handling is separated by boundary:

- **Dictionary keys:** duplicate keys collapse before assembly under the existing dictionary behavior; later assignment replaces the earlier value. Identity does not recover or represent overwritten pre-assembly values.
- **Component identities:** two assembled entries with the same complete identity are invalid and fail closed, whether their content or digests match or differ. They must not be silently deduplicated.
- **Effective reconstructed occurrences:** each source component must correspond to exactly one effective occurrence. Zero, multiple, or ambiguously corresponding occurrences fail the Blocker 3 one-to-one coverage requirement and invalidate eligibility. Matching content or digest does not permit deduplication or substitution.

## 8. Empty, absent, and null states

Content state does not change a structural component identity, but distinct representable states must not alias in canonical content:

| State | Structural presence | Canonical content treatment |
| --- | --- | --- |
| absent fixed slot | fixed identity remains present | `ABSENT`, canonical bytes `{"state":"absent"}` |
| empty string | component is present | `TEXT`, zero canonical text bytes |
| empty mapping | component is present | `EMPTY_MAPPING`, canonical bytes `{}` |
| empty list | component is present | `EMPTY_LIST`, canonical bytes `[]` |
| missing dictionary key | no component and no identity exists | no absent keyed component is invented |
| explicit JSON `null` / representable present `None` | component is present | `JSON`, canonical bytes `null`, distinct from `ABSENT` |

For a fixed slot whose current boundary expressly represents `None` as absence, that value uses the existing `ABSENT` treatment rather than inventing a present-null state. Elsewhere, a representable explicit null is present JSON. Absent fixed slots, empty strings, empty mappings, empty lists, and present null therefore remain distinct exactly at the existing canonical boundary.

The stage-coordinate markers also distinguish absent from present-empty stage identity. Task absence is structural and frozen as `task-absent`; it is not a content value.

## 9. Evaluation consequences

Deterministic evaluation uses the complete identity tuple for correspondence, the separately validated manifest order for sequence, and exact canonical UTF-8 bytes for Blocker 3 equivalence. Changed and unchanged content, duplicates, empty and absent inputs, identity mismatch, malformed versions, and collision simulation must receive deterministic fail-closed results.

This identity contract grants no authority to omit or transform any component. Blocker 5 remains explicitly unresolved. This document does not define baseline lifetime, baseline coordinates or trust, delta format, cache key, provider reuse, activation, fallback mechanics, telemetry changes, or persistence.

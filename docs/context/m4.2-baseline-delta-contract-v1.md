# M4.2 Baseline and Delta Contract v1

## 1. Status and authority boundary

This document is planning authority input for M4.2 Blocker 5 only. It defines baseline coordinates, lifetime, trust, invalidation, exact delta semantics, and atomic reconstruction equivalence. It is not implementation authority and does not authorize M4.2 implementation, production-code changes, test changes, persistence, cache behavior, provider-boundary reuse, omission, or savings claims.

The approved authority-equivalence and identity contracts remain controlling. In particular, selection or unchanged classification is not omission or reuse authority. M4.2 implementation remains blocked.

## 2. Baseline meaning

A baseline is an ephemeral exact snapshot and representation of one fresh exact assembly for one logical request under one approved coordinate set. It preserves the complete ordered component identity sequence and the canonical content needed to validate and reconstruct that assembly exactly.

A baseline is not lifecycle authority, persistent cache authority, cross-run trusted state, or a source of truth replacing repository or request sources. Current repository and request sources must still be assembled freshly to establish the current exact assembly against which any delta is determined and any reconstruction is validated.

## 3. Baseline coordinates

The minimum `baseline_coordinate` is the following ordered structural record:

```text
(
  identity-namespace,
  identity-version,
  stage-coordinate,
  task-coordinate,
  complete-ordered-component-identity-sequence,
  canonicalization-id
)
```

The values are frozen as follows:

- identity namespace: `sdd.context.component`;
- identity version: `m4.2-v1`;
- stage coordinate: the approved present, present-empty, or absent stage coordinate from the identity contract;
- task coordinate: the literal `task-absent`, because the approved request model has no explicit task identity;
- component identity sequence: every complete component identity, in fresh exact assembly order, with no omission, duplication, substitution, or inferred identity; and
- canonicalization ID: `sdd.canonical.utf8-sorted-compact-v1`.

No task identity may be invented or inferred. Identity remains the approved tuple `(namespace, version, stage-coordinate, task-coordinate, component-coordinate)`; sequence position is validated separately and is not added to component identity.

The controlled evaluation/execution scope that owns the baseline is an additional eligibility boundary, not a new identity coordinate. A baseline created in another scope is ineligible even if all structural coordinate values match. No filename, path, timestamp, process value, provider value, or cache value enters the baseline coordinate.

## 4. Baseline lifetime and trust

Baseline lifetime is limited to the single controlled evaluation/execution scope in which fresh exact assembly produced it. The baseline is evaluation-local or execution-local and in-memory only. Durable persistence, cross-process trust, and cross-run trust are forbidden. This contract defines no persistence or cache policy and does not resolve Blocker 10.

A baseline is trusted for consideration only when all of the following validate:

- it was produced directly from fresh exact assembly in the current controlled scope;
- its complete ordered identity sequence is known;
- canonical content and SHA-256 digests are available wherever required for deterministic comparison, with exact canonical bytes remaining the final content test;
- authority coverage is exactly 100% under one-to-one component and required-position correspondence;
- authority byte mismatch is exactly 0;
- no duplicate identity, collision, ambiguity, malformed identity, or ambiguous source-to-effective mapping exists; and
- its namespace, version, stage coordinate, task coordinate, and canonicalization ID are recognized and well formed.

Trust must never be inferred from age, recency, filename, path, cache hit, provider response, prior success, digest equality alone, or any similar proxy.

## 5. Deterministic invalidation

Invalidation has two distinct outcomes:

1. **Full-baseline invalidation:** the baseline is not a permissible reconstruction base. It must be discarded for optimized reconstruction.
2. **Direct-reuse invalidation with delta eligibility:** the baseline is not itself the current exact assembly, but a precise component difference may be represented as a delta if the baseline remains trusted, the common coordinate envelope remains valid, and all current fresh-assembly facts are unambiguous.

The following cause full-baseline invalidation:

- stage coordinate change;
- task coordinate change;
- identity namespace or version mismatch, including an unrecognized value;
- canonicalization mismatch or an unrecognized canonicalization ID;
- duplicate component identity;
- identity collision or any identity/content correspondence ambiguity;
- malformed or incomplete baseline metadata;
- absence of canonical content or other required validation material;
- failure to establish that the baseline came from fresh exact assembly in the current controlled scope;
- authority coverage below 100% or not determinable;
- authority byte mismatch other than 0 or not determinable; or
- a missing required authority-protected component in either the baseline or the proposed reconstruction.

Within an otherwise valid common envelope, the following invalidate direct unchanged reuse and require an exact delta rather than full-baseline invalidation when they are safely and unambiguously distinguishable against current fresh exact assembly:

- changed canonical content at the same complete component identity: `changed`;
- a component present only in current fresh exact assembly: `added`;
- a component present only in the baseline: `removed`, unless it is required authority-protected content, in which case reconstruction is ineligible and fails closed;
- a changed complete component identity: one exact `removed` identity plus one exact `added` identity, never an inferred rename;
- a complete component sequence change caused by exact additions, removals, or ordering changes; and
- an ordering change: `reordered` when order affects effective provider input.

A component sequence change is therefore never silently accepted. It is either fully and exactly explained by an eligible delta or it makes reconstruction invalid. Any unexplained sequence difference, missing identity, extra identity, ambiguous pairing, duplicate occurrence, substitute component, or ordering ambiguity causes full-baseline invalidation.

These rules define validation, not cache eviction.

## 6. Delta meaning and categories

A delta is the exact component changes required to reconstruct the current fresh exact assembly from a valid baseline. It is derived by deterministic comparison of the baseline with current fresh exact assembly using complete component identity, separately validated order, and exact canonical content.

A delta is not a summary, semantic patch, lossy patch, inferred change, rename inference, transformation, or digest-only assertion. No wire format is defined.

Every baseline/current occurrence must receive an unambiguous category:

- `unchanged`: the same complete identity has exactly equal canonical bytes and its required effective position is preserved;
- `added`: a complete identity exists only in current fresh exact assembly;
- `removed`: a complete identity exists only in the valid baseline, subject to the authority-protection restriction in Section 5;
- `changed`: the same complete identity exists in both, but exact canonical bytes differ; and
- `reordered`: an otherwise corresponding occurrence changes required effective position where ordering changes effective provider input.

Digest equality is only a necessary unchanged-content check. `unchanged` still requires exact canonical-byte equality, unambiguous one-to-one identity correspondence, and required ordered position. Categories may record ordering independently where needed to explain the exact resulting sequence; counts must be deterministic and must not conceal overlapping conditions.

## 7. Reconstruction invariant

For every eligible reconstruction:

```text
reconstructed effective ordered provider input
==
fresh exact assembly effective ordered provider input
```

Equality is deterministic and complete over the full ordered component sequence, each complete component identity, each corresponding occurrence, and exact canonical content. Matching bytes at another identity or position do not satisfy the invariant. The reconstruction must contain exactly the components and ordering that fresh exact assembly produces, with no missing, extra, duplicate, substituted, transformed, or ambiguous occurrence.

Authority coverage must equal 100%. Authority byte mismatch must equal 0. The ordered authority-protected projection must also equal the corresponding projection of fresh exact assembly. Semantic similarity, digest equality alone, or partial sequence equality is insufficient.

## 8. Atomic reconstruction and failure behavior

Reconstruction is validated as one whole candidate before any optimized dispatch. Baseline validity, delta validity, complete ordered reconstruction, exact-match equivalence, authority coverage, and authority byte equivalence must all succeed before the candidate can be considered further.

No partial reconstructed input may be dispatched. If any baseline, delta, identity, ordering, content, authority, metadata, or whole-reconstruction validation fails, the optimized reconstruction is discarded in full. Required behavior is fresh exact assembly and exact inclusion.

This contract defines no runtime try/catch structure, retry mechanic, dispatch implementation, or provider-call behavior. It does not alter the approved rule that optimized activation permits an attempt but does not guarantee optimized dispatch.

## 9. Eligibility boundaries and non-authorization

The following decisions are independent and must not be collapsed:

- **Component unchanged eligibility:** exact identity, exact canonical bytes, and required position establish only that a component is unchanged.
- **Baseline validity:** all coordinate, scope, provenance, trust, authority, and metadata checks establish only that the baseline may be considered as a reconstruction base.
- **Delta reconstruction validity:** the exact changes must reconstruct and validate the complete current fresh exact assembly.
- **Omission/reuse authorization:** neither unchanged classification, baseline validity, nor reconstruction validity alone authorizes omission or reuse.
- **Provider-boundary reuse:** proof that unchanged provider-bound bytes can avoid retransmission is outside Blocker 5 and remains Blocker 6.

Blocker 5 establishes no provider-boundary savings, provider reuse, token savings, byte savings, cache savings, or percentage reduction.

## 10. Planning-only fields and metrics

The following concepts are frozen for deterministic planning and evaluation. They may remain evaluation-local or in-memory and do not amend any telemetry schema:

| Field or concept | Planning meaning |
| --- | --- |
| `baseline_coordinate` | Complete ordered record defined in Section 3. |
| `baseline_component_count` | Exact integer count of component occurrences in the baseline sequence. |
| `baseline_identity_sequence` | Complete ordered sequence of full component identities. |
| `baseline_canonicalization_id` | Exact recognized content canonicalization ID. |
| `delta_added_count` | Exact count of `added` occurrences. |
| `delta_removed_count` | Exact count of `removed` occurrences. |
| `delta_changed_count` | Exact count of `changed` occurrences. |
| `delta_reordered_count` | Exact count of occurrences whose required effective position changed. |
| `reconstruction_component_count` | Exact integer count of component occurrences in the complete reconstructed sequence. |
| `reconstruction_exact_match` | Boolean true only when the full invariant in Section 7 succeeds. |
| `baseline_invalid_reason` | Deterministic reason for baseline ineligibility; absent only when baseline validation succeeds. Multiple failures must not be hidden by an assertion of validity. |

Counts do not establish trust or equivalence by themselves. `reconstruction_exact_match` cannot be true unless component count, identity sequence, order, exact canonical content, authority coverage, and authority byte mismatch all satisfy this contract.

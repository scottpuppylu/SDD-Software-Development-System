# M4.3 Provenance Boundary v1

## 1. Scope

This document resolves only the M4.3 planning question of whether a future provenance semantic boundary is necessary and, if so, the minimum safe authority contract for it. It does not implement that boundary or authorize a new M4.3 reduction candidate.

All frozen M4.3 rules remain unchanged: authority coverage is 100%; authority byte mismatch is 0; `UNKNOWN`, `MIXED_AUTHORITY`, and governance remain exact and fail closed; task identity remains task-absent with no inference; `BASELINE` remains the default; public modes remain `BASELINE` and `OPTIMIZED`; provider/subprocess calls remain capped at one; there is no post-dispatch `BASELINE` retry or partial optimized dispatch; the provider boundary remains `SELF_CONTAINED_FULL_INPUT`; provider-side reuse, persistence, and cross-run trust remain unauthorized; telemetry schema remains 1.0.4; and `GIT_HISTORY` remains the only currently reducible component.

## 2. Existing blocker

`StageRunner._collect_runtime_inputs()` creates `GIT_STATUS` and `CURRENT_BRANCH` values internally and returns them in a plain runtime-input mapping. `StageRunner` passes that mapping into `StageExecutionRequest.runtime_inputs`. The request definition supplies no provenance semantics, and arbitrary callers can construct the same request field with the same keys. The compiler iterates `request.runtime_inputs` and currently classifies runtime entries from the key, without a provenance distinction.

Consequently, runner-produced and arbitrary caller-supplied values with the same key are structurally indistinguishable at the classification seam. Key names, stage association, source role, and compiler coordinate cannot prove producer origin.

## 3. Provenance necessity

`PROVENANCE_SEMANTICS_REQUIRED = YES`.

M4.3 cannot safely promote a caller-accessible `UNKNOWN` runtime component to a reducible candidate without a provenance distinction. Reduction or omission would otherwise apply to an arbitrary caller value merely because it occupies the same key or stage coordinate as an internally produced value. That would replace structural proof with inference and could remove unclassified caller-supplied content. Exact fail-closed treatment is therefore required unless trusted internal origin is explicitly provable.

## 4. Minimal semantic model

The minimum conceptual model has two states:

- `TRUSTED_INTERNAL_RUNTIME`: explicit structural provenance proves that the value came from the authorized internal runtime producer and that this provenance survived intact to the compiler decision.
- `UNTRUSTED_OR_UNPROVEN_RUNTIME`: every other case, including caller-supplied, missing, malformed, lost, ambiguous, or otherwise unprovable provenance.

No third state is necessary for this planning boundary. Uncertainty is deliberately collapsed into `UNTRUSTED_OR_UNPROVEN_RUNTIME` so that it receives exact fail-closed treatment. These are semantic states only, not an implementation enum or API design.

## 5. Trust origin

Trust may be established only by explicit structural producer provenance originating at the authorized internal production event and preserved through the required handoff. For the inspected seam, that origin is value creation inside `StageRunner._collect_runtime_inputs()`. Creation there is a necessary origin fact, but downstream trust exists only if that fact is explicitly and structurally conveyed; the value content alone does not carry trust.

The evaluated trust claims are:

- A. Value created inside `StageRunner._collect_runtime_inputs()`: eligible origin for trust, but not sufficient at the compiler unless explicit structural producer provenance survives the handoff.
- B. `StageExecutionRequest` key name: does not establish trust.
- C. `.sdd/stages.yaml` requirement or stage mapping: does not establish trust.
- D. Caller-provided `runtime_inputs` value: does not establish trust.
- E. Content grammar matching expected Git output: does not establish trust.

Trust is never inferred from content, key, stage association, declared requirement, source role, or compiler coordinate.

## 6. Propagation and lifetime

Provenance must have the narrowest lifetime that still permits the compiler to make a safe eligibility decision:

1. Producer to `StageExecutionRequest` construction: **required**. The structural origin fact must survive the producer/handoff boundary.
2. `StageExecutionRequest` to `ContextCompiler`: **required**. The compiler must receive provable provenance associated with the applicable value.
3. Compiler to manifest/selection: **required only through the compiler's classification and selection decision**. Provenance must remain available until eligibility is decided, but it need not become a manifest field or survive in compiler output.
4. Provider dispatch: **not required and not authorized**. Provenance must be discarded before or at completion of compiler selection and need not enter provider payloads.
5. Persistence: **not required and not authorized**.
6. Telemetry: **not required and not authorized**.
7. Lifecycle state: **not required and not authorized**.

Thus the provenance contract is per-request, in-memory, and ephemeral. It creates no cross-run trust.

## 7. Public API boundary

A safe future solution does not inherently require changing public `StageExecutionRequest` fields, defining a new public `runtime_inputs` schema, adding user-visible configuration, or adding a lifecycle field. The required contract is an internal structural handoff semantic. This planning decision does not select or authorize a representation for that handoff.

`PUBLIC_API_CHANGE_REQUIRED = NO`. If a later implementation cannot preserve provenance internally without a public change, that is a new blocker requiring separate approval; it is not permission to expand this boundary.

## 8. Fail-closed semantics

If trusted internal provenance is absent, malformed, lost, ambiguous, or not provable, the runtime component must be classified as `UNTRUSTED_OR_UNPROVEN_RUNTIME`, preserved byte-exact, and excluded from reduction or omission eligibility. Trust must not be inferred from content, key, stage mapping, declared requirement, source role, or compiler coordinate.

This rule preserves exact treatment for `UNKNOWN` and `MIXED_AUTHORITY`. Failure or uncertainty cannot trigger a retry, partial optimized dispatch, or any fallback that increases provider-call cardinality beyond one.

## 9. Effect on candidate eligibility

This provenance contract resolves only the shared provenance blocker. It does not promote `GIT_STATUS` or `CURRENT_BRANCH` to `M4_3_CANDIDATE`, and it does not authorize reducing or omitting either component.

Each component still requires separately approved evidence establishing all of the following:

- a closed content contract;
- a useful deterministic reduction or omission policy;
- a semantic safety proof; and
- a controlled evaluation contract.

Until those requirements and separate project authorization are satisfied, `GIT_HISTORY` remains the only reducible component.

## 10. Authorization boundary

This document is planning only. It does not authorize production implementation, production-code changes, test changes, new request fields, public API changes, lifecycle changes, telemetry changes, persistence, cross-run trust, provider payload fields, provider-side cache or reuse, task identity or task-identity inference, automatic token budgeting, semantic retrieval or ranking, authority summarization or substitution, an implementation slice, actual candidate promotion, or a commit.

Implementation remains blocked pending project approval. No new M4.3 reduction candidate is authorized.

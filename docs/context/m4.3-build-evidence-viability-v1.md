# M4.3 Build Evidence Viability v1

## 1. Scope

This Round 4 evidence review evaluates only `runtime_inputs["BUILD_LINT_TYPECHECK_EVIDENCE_IF_APPLICABLE"]`. It uses the authorized M4.3 classification and authorization boundary, the applicable provenance rule, the Stage 09 declaration, and the runtime producer and its directly called compaction helper. It does not inspect or decide any other runtime component, provider behavior, telemetry implementation, tests, repository history, or external material.

The decision is evidence and policy viability only. It makes no production or test change and grants no implementation authority.

## 2. Frozen assumptions

Authority coverage remains 100% and authority byte mismatch remains 0. `UNKNOWN`, unproven provenance, `MIXED_AUTHORITY`, and governance remain exact. Task identity remains absent. `BASELINE` remains the default and `OPTIMIZED` remains an explicit attempt only. Provider/subprocess calls remain capped at one, with no post-dispatch retry and no partial optimized dispatch. The telemetry schema remains 1.0.4. Persistence and provider-side reuse remain unauthorized. The provider boundary remains `SELF_CONTAINED_FULL_INPUT`. Token-budget truncation and semantic summarization/ranking remain unauthorized. `GIT_HISTORY` remains the only currently reducible component unless a separately approved future candidate is established.

## 3. Producer output contract

1. The produced value is a `dict[str, str]` mapping when the internal producer handles the requested runtime key. If `.sdd/evidence` does not exist, the branch assigns `{}` directly.
2. Evidence-file-dependent keys are repository-relative POSIX paths for recursively discovered `*.json` files that are files, parse successfully, and fit the aggregate limit. Three producer marker keys can also appear: `__unreadable_evidence__` conditionally, `__skipped_evidence_size_limit__` conditionally, and `__context_diet__` whenever `_collect_evidence_summary()` runs.
3. The path keys are not a fixed closed set. They depend on evidence files. The three marker names are fixed, but two are conditional.
4. Every outer mapping value is a string. A normal evidence value is compact JSON text, possibly followed by `\n<omitted: evidence summary file limit>`. The unreadable and aggregate-limit marker values are newline-joined relative paths. The context-diet value is fixed explanatory text.
5. Bounds are differentiated. The compaction helper limits nesting to depth 6, strings to 2,000 characters plus an explicit omission marker, and lists to 50 items plus an explicit omission marker. It replaces named noisy values with omission markers. A serialized evidence file is limited by a 16,000-byte slice, after which the explicit file-limit marker is appended, so that final value can exceed 16,000 bytes by the marker length. Accepted serialized evidence bytes are limited by a 200,000-byte aggregate counter. The two newline-joined path-marker values have no separately proven character/byte or entry-count bound in the inspected code; the fixed context marker is bounded by its literal. Therefore the producer is intentionally bounded in evidence content and accepted evidence-file bytes, but the code does not prove a strict bound on every byte of the final outer mapping.
6. Noisy fields are already removed as raw content. Case-insensitive keys `stdout`, `stderr`, `prompt`, `request`, `response`, `provider_output`, `provider_stdout`, `provider_stderr`, `codex_output`, `codex_stdout`, `codex_stderr`, `transcript`, `diff`, `patch`, and `raw_output` retain their key but replace their value with a count-bearing or generic omission marker.
7. File-size controls are already enforced: a 16,000-byte per-file serialized-content limit and a 200,000-byte aggregate accepted-content limit, using the default arguments shown by code.
8. Omission is explicit. Per-file truncation appends a file-limit marker; files excluded by the aggregate limit are listed under `__skipped_evidence_size_limit__`; unreadable or invalid JSON files are listed under `__unreadable_evidence__`; depth, list, long-string, and noisy-value reductions also emit explicit markers.
9. The produced mapping can be empty only through the producer branch used when the evidence root does not exist. Once `_collect_evidence_summary()` runs, it always adds `__context_diet__`, including for an empty evidence directory.
10. Outer key insertion order is deterministic for a fixed repository state: eligible JSON paths are sorted, conditional marker keys are appended in fixed order, and `__context_diet__` is last. The inspected code does not sort keys inside parsed JSON objects; their compact JSON text follows the parsed input object's iteration order. No stronger ordering claim is made.
11. Yes. The docstrings and fixed `__context_diet__` text expressly describe the output as a compact, bounded Stage 09 projection that removes verbose provider/Codex transcripts and related raw material while retaining structured audit facts and explicit omission information.

## 4. Provenance result

Arbitrary callers can supply the same runtime key through the plain runtime-input mapping. The inspected provenance authority establishes that key name, stage association, declared requirement, content shape, source role, and compiler coordinate do not distinguish caller values from internally produced values. No structural discriminator presently proves origin at the classification seam.

`BUILD_LINT_TYPECHECK_EVIDENCE_PROVENANCE = MIXED_OR_UNPROVEN`.

Policy viability below is considered only under the planning assumption that a future, separately approved provenance mechanism could prove `TRUSTED_INTERNAL_RUNTIME`. Caller-supplied, missing, malformed, lost, ambiguous, or otherwise unproven provenance must remain exact. This document does not authorize provenance implementation.

## 5. Stage 09 semantic role

Stage 09 is `VERIFICATION_AND_CONVERGENCE`, a gate with `PASS`, `FAIL`, and `INCOMPLETE` results. It reads implementation evidence, requires `BUILD_LINT_TYPECHECK_EVIDENCE_IF_APPLICABLE` as a runtime input, and explicitly includes the `BUILD_LINT_TYPECHECK` check. Its result routes PASS to Stage 10, FAIL to classification, and INCOMPLETE to remediation.

Accordingly, complete available build/lint/typecheck evidence is potentially relevant to all three gate outcomes. Removing an evidence-file key could suppress a failure, blocker, or proof needed for verification. Removing fields from its compact JSON text could conceal verification facts. Authority does not establish equivalence between component absence, the producer's `{}` when the evidence root is absent, and a present summary with only `__context_diet__` when no applicable JSON evidence is collected. Explicit unreadable, skipped-size, truncation, and other omission markers communicate evidence limitations and are semantically meaningful to an evidence-sufficiency decision. No inspected authority permits treating them as redundant.

## 6. Policy viability

### D1. DROP_EMPTY_MAPPING

Not viable. The component is a declared Stage 09 runtime requirement, and authority does not equate absent with present-empty or prove that `{}` means no applicable evidence rather than unavailable evidence. Dropping it could alter an `INCOMPLETE` determination or conceal a missing-evidence condition.

### D2. DROP_EMPTY_VALUES

Not viable. Internally collected normal values are JSON text and therefore even empty JSON strings, lists, and objects serialize as non-empty strings. Arbitrary caller mappings remain exact, and no authority establishes that an empty string value under an evidence identity is semantically equivalent to removing that identity.

### D3. DROP_NOISY_FIELDS_AGAIN

No further policy is viable. The producer already performs the deterministic noisy-field projection and keeps explicit omission markers. Repeating the same transformation downstream is redundant and has no non-zero practical reduction on internally produced output; removing the retained keys or markers would be a different, unproven semantic transformation.

### D4. FIELD_ALLOWLIST

Not viable. Evidence keys are file-dependent paths, and the authorized sources provide no closed allowlist of evidence files or inner verification fields. An allowlist could remove evidence needed by the explicit Stage 09 check.

### D5. FIELD_SIZE_BOUND

No further bound is viable. The producer already bounds depth, string length, list length, serialized per-file content, and aggregate accepted evidence content, with explicit limitation markers. Further bounding would risk hiding verification evidence or evidence-sufficiency markers. The lack of a separately proven final-map bound for path lists does not establish a semantically safe additional truncation rule.

### D6. COLLAPSE_DUPLICATES

Not viable. Exact string equality can mechanically identify duplicate values, but the distinct path keys identify distinct evidence files. No authority proves that repeated contents make those evidence occurrences semantically redundant or that one identity can represent the others without affecting completeness and traceability.

### D7. OMIT_SKIPPED_MARKERS

Not viable. Skipped-size and other omission markers disclose that evidence was not fully available in the projection. Removing them could make incomplete evidence appear complete and affect PASS/FAIL/INCOMPLETE reasoning.

## 7. Usefulness assessment

No evaluated policy satisfies the usefulness gate. Even assuming future trusted internal provenance, none has a proven Stage 09 semantic-equivalence rule. Several transformations could reduce provider-bound bytes in selected inputs, but byte reduction alone cannot justify suppressing verification evidence or explicit limitation state. Reapplying the existing noisy-field reduction has zero practical effect. No exact policy simultaneously proves non-zero practical reduction, semantic safety, fail-closed ambiguity handling, and benefit commensurate with implementation complexity.

Therefore no policy ID is created, no directly controlled provider-bound reduction is proven, and no new M4.3 candidate is promoted.

## 8. Controlled evaluation requirements

Because no policy is promoted, there is no candidate-specific future evaluation contract to authorize. Any later separately approved candidate would have to cover, at minimum: eligible trusted evidence mapping; ineligible trusted mapping; caller or unproven provenance; empty mapping; empty values; skipped-size markers; malformed or ambiguous structure; `BASELINE` versus `OPTIMIZED` semantic equality; authority coverage 100%; authority byte mismatch 0; semantic, lifecycle, and gate regression 0; provider/subprocess calls at most 1; directly observed provider-bound request bytes; and full-suite PASS.

No provider-token claim is valid without attributable structured usage accepted by telemetry schema 1.0.4.

## 9. Authorization boundary

This document does not authorize provenance implementation, production changes, test changes, public API changes, lifecycle changes, telemetry changes, persistence, provider cache/reuse, task identity, automatic context budgeting, authority summarization, semantic retrieval/ranking, or candidate implementation. It does not authorize a commit. Implementation remains blocked pending separate project approval.

# M4.2 Provider-Boundary Proof v1

## 1. Status and authority boundary

This document is planning authority input for M4.2 Blocker 6 only. It is not implementation authority. It does not authorize production or test changes, provider caching, provider/model routing, conversation or session persistence, call-cardinality changes, telemetry-schema changes, or resolution of Blockers 7-10.

The proof uses only the approved M4.2 contract sections and the current executor/provider dispatch and request-building surfaces. It does not infer capability from external provider knowledge.

## 2. Current provider boundary

The current compiled-context dispatch boundary supplies a complete `StageExecutionRequest` to an executor. `ContextDispatchCoordinator.execute()` either calls `executor.execute(package.request)` or calls `executor.prepare(package.request)` followed once by `executor.dispatch(prepared)` (`sdd_orchestrator/context_dispatch.py:36-72, 113-118`). The request contains stage identity and type, core question, contract, artifacts, semantic inputs, runtime inputs, and optional stage instructions (`sdd_orchestrator/executor.py:10-23`).

The supported execution paths inspected are:

1. `CodexExecReasoningExecutor`: `_provider_system_instructions()` and `_provider_user_input()` render the complete request. `build_prompt()` concatenates those strings. `prepare()` stores that complete prompt, and `dispatch()` starts `codex exec` and supplies the prompt as subprocess stdin (`sdd_orchestrator/providers.py:152-175, 280-337`). The command uses `--ephemeral` by default and contains no continuation or reusable-context argument (`sdd_orchestrator/providers.py:250-299`).
2. `OpenAIResponsesExecutor`: `prepare()` builds a complete request body containing `model`, complete `instructions`, complete `input`, output limit, and response schema, then serializes the body to UTF-8 JSON bytes. `dispatch()` sends those bytes in one HTTP POST to `/v1/responses` (`sdd_orchestrator/providers.py:412-481`). The constructed body contains no prior-response, conversation, session, cached-prefix, reusable-context, or delta reference.
3. `ExternalCommandExecutor`: `prepare()` serializes the complete `StageExecutionRequest.to_dict()` as JSON, and `dispatch()` supplies that JSON as subprocess stdin (`sdd_orchestrator/executor.py:77-114`). The executor protocol and serialized request expose no prior-context or provider-side reuse handle.

Each inspected call is therefore self-contained at the repository-controlled boundary. No prior request context is implicitly referenced by the constructed call. The current supported call surface exposes no reusable context handle, cached-prefix ID, conversation/session continuation ID, server-side cache reference, or equivalent mechanism.

This is a statement about current repository behavior only. It is not a statement about any external provider's unexposed capabilities.

## 3. Retransmission proof

Classification: **A. retransmitted on every eligible provider call**.

For Codex, the complete generated prompt is supplied on stdin for every dispatch. For OpenAI Responses, the complete serialized `instructions` and `input` are included in every HTTP request body. For the external-command path, the complete serialized stage request is supplied on stdin for every dispatch. No inspected call construction can replace unchanged request content with a reference to prior provider-held content.

Consequently, local baseline/delta reuse does not prove provider-boundary byte avoidance. With the current boundary, a complete effective input must still be assembled and transmitted on each eligible call.

## 4. Effective-input equivalence

Any future provider-boundary reuse is valid only if:

```text
reconstructed effective ordered provider input
==
fresh exact assembly effective ordered provider input
```

The equality is exact and ordered, not semantic. Authority coverage must equal 100%, and authority byte mismatch must equal 0. Matching meaning, digest equality alone, transformed content, or matching bytes at another occurrence or position is insufficient.

No current provider-boundary reference mechanism exists on which to prove this equivalence while omitting unchanged transmitted bytes. The absence of such a mechanism must fail closed to fresh exact assembly and exact inclusion.

## 5. Local reuse versus provider reuse

The following are distinct and must not be counted as one another:

- local detection may identify components whose identity, canonical bytes, and required position are unchanged;
- local baseline/delta reconstruction may reconstruct the complete exact ordered provider input;
- local work may avoid some recomputation or copying if a future authorized implementation proves that effect;
- bytes are omitted from the provider-bound request only when the actual dispatched stdin or HTTP body excludes them through a supported exact reuse mechanism; and
- provider-side reuse exists only when the provider boundary supports and uses a reference to unchanged context while preserving exact effective input.

The first three do not establish either of the last two. Local delta bytes, local representation size, or avoided local work must not be reported as provider savings.

## 7. Provider-boundary proof result

`PROVIDER_BOUNDARY_REUSE = NOT_SUPPORTED_BY_CURRENT_BOUNDARY`.

This negative proof resolves Blocker 6 for planning. M4.2 may still proceed, once separately authorized and all remaining blockers are resolved, with local context-selection and reconstruction work; it must not claim provider-input savings. Any future provider reuse requires a separately approved provider-specific capability and contract that proves exact effective-input equivalence.

## 8. Measurement consequences

`provider_unchanged_bytes_avoided` may be non-zero only when actual provider-boundary evidence proves that those bytes were not transmitted while the provider's effective ordered input remained exactly equal to fresh exact assembly.

Under the current boundary, no such omission mechanism exists. The value must therefore be unavailable/not proven, or zero only where the applicable measurement semantics make zero a factual observation of the transmitted request. It must not be inferred from local delta bytes, unchanged-component counts, local representation size, or local avoided work.

No provider token savings may be inferred. Codex CLI `tokens used` is not provider-token evidence. This document does not amend the telemetry schema.

## 9. No provider savings claims

The current supported boundary does not prove actual token savings, provider-cache savings, or provider-byte savings. None may be claimed. A local exact reconstruction can prove correctness of effective input, but cannot prove that the provider received unchanged context without retransmission.

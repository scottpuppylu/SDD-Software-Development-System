# M4.3 Runtime Git Evidence v1

## 1. Scope

This Round 1 evidence resolution is limited to `runtime_inputs["GIT_STATUS"]` and `runtime_inputs["CURRENT_BRANCH"]`. It determines only whether either component has enough evidence to become an `M4_3_CANDIDATE` for a future, separately approved deterministic reduction or omission policy. It does not create such a policy and does not authorize production behavior, test changes, or a commit.

The evidence reviewed was limited to the authorized portions of the M4.3 operational reduction plan, the Stage 08 `required_inputs.runtime` declaration, the runner producer path for the two values, and the compiler runtime-input classification and assembly path.

## 2. Frozen authority

The frozen boundary remains unchanged: authority coverage is 100%, authority byte mismatch is 0, `UNKNOWN` and `MIXED_AUTHORITY` fail closed to exact, governance remains exact, and task identity remains `task-absent` with no inference. `BASELINE` remains the default; `OPTIMIZED` is an explicit attempt only. A candidate must be wholly prepared and validated before dispatch, with no partial optimized dispatch, no post-dispatch retry, and at most one provider or subprocess call. Telemetry remains schema 1.0.4. Persistence and provider-side reuse remain unauthorized, and the provider boundary remains `SELF_CONTAINED_FULL_INPUT`.

`GIT_HISTORY` remains the only currently reducible component.

## 3. GIT_STATUS evidence

### A. Producer provenance

- The runner-created value is internal: `_collect_runtime_inputs` adds the key only when the stage runtime declaration requests `GIT_STATUS`, and obtains its value through `_git`.
- The value is not always internally produced at the compiler boundary. `ContextCompiler.compile_baseline` and `compile_optimized` accept a `StageExecutionRequest`; baseline assembly iterates `request.runtime_inputs` directly. An arbitrary caller-supplied value under the `GIT_STATUS` key therefore reaches the same compiler path as a runner-created value.
- No inspected structure marks a runtime input as runner-produced or distinguishes it from arbitrary caller input. The key, stage association, source role, and compiler coordinate are shared and are not provenance evidence.

Result: provenance is `MIXED_OR_UNPROVEN`.

### B. Content contract

- Exact command: `git status --porcelain=v1`, executed with the repository root as the working directory.
- Capture and decoding: stdout and stderr are captured as text with UTF-8 decoding and replacement for decoding errors.
- Exact normalization: successful stdout is converted by `(proc.stdout or "").strip()`. This removes leading and trailing whitespace; no per-line validation or other normalization is present.
- Empty value: possible in the repository path because successful empty stdout normalizes to `""`; the code does not reject it.
- Multiline content: possible at the repository boundary because the complete stripped stdout is returned and no newline or line-count restriction is applied.
- Failure behavior: because `allow_failure` is not enabled for this call, a nonzero return code raises `StageExecutionValidationError`; the error includes stripped stderr. No runtime value is returned on that path.
- Closed deterministic grammar: not proven. The inspected code constrains the command, decoding, outer `strip`, and failure handling, but it accepts the resulting stdout without validating a closed grammar. No closed set of line forms, characters, ordering rules, or ambiguity checks is established by repository code.

Result: content contract is `INCOMPLETE`.

## 4. CURRENT_BRANCH evidence

### A. Producer provenance

- The runner-created value is internal: `_collect_runtime_inputs` adds the key only when the stage runtime declaration requests `CURRENT_BRANCH`, and obtains its value through `_git`.
- The value is not always internally produced at the compiler boundary. The compiler accepts a `StageExecutionRequest` and directly assembles every item in `request.runtime_inputs`; arbitrary caller-supplied `CURRENT_BRANCH` content reaches the same coordinate.
- No inspected structural marker distinguishes runner-produced output from arbitrary caller input. Neither the key nor Stage 08 association proves provenance.

Result: provenance is `MIXED_OR_UNPROVEN`.

### B. Content contract

- Exact command: `git branch --show-current`, executed with the repository root as the working directory.
- Capture and decoding: stdout and stderr are captured as text with UTF-8 decoding and replacement for decoding errors.
- Exact normalization: successful stdout is converted by `(proc.stdout or "").strip()`.
- Empty value: possible in the repository path because successful empty stdout normalizes to `""`; the code does not reject it.
- Failure behavior: because `allow_failure` is not enabled for this call, a nonzero return code raises `StageExecutionValidationError`; the error includes stripped stderr. No runtime value is returned on that path.
- Detached HEAD behavior: `UNKNOWN`. The inspected repository code has no detached-HEAD branch and establishes no command-output semantics for that state beyond applying the common stdout normalization or nonzero-exit failure path.
- Closed deterministic grammar: not proven. The inspected code does not validate a single-line branch-name grammar, reject multiline stdout, constrain characters, or distinguish an empty result by cause.

Result: content contract is `INCOMPLETE`.

## 5. Stage 08 mapping

Stage 08 declares these exact runtime requirements under `required_inputs.runtime`:

```text
GIT_STATUS
CURRENT_BRANCH
RECENT_COMMITS
```

This proves positive stage-required relevance for `GIT_STATUS` and `CURRENT_BRANCH` in Stage 08. It does not prove safe omission in any other stage. The frozen rule remains `STAGE_NOT_REQUIRED => NO AUTOMATIC OMISSION`.

## 6. Candidate decision

Both components are non-authority, non-governance, and operational under the current M4.3 plan. Task identity is not needed, and a future local pre-dispatch omission or reduction would make the complete self-contained provider-bound input smaller whenever it actually removes nonempty bytes.

Neither component passes the full safe-candidate test, however. The inspected compiler boundary admits arbitrary request values under the same keys, provides no trusted-producer discriminator, and classifies each non-`GIT_HISTORY` runtime input as `UNKNOWN` with `EXACT_REQUIRED` treatment. The inspected producers also do not enforce closed content grammars. Consequently, ambiguity cannot be separated into an eligible trusted class using existing structure; it must continue to fail closed to exact.

`GIT_STATUS` remains `INSUFFICIENT_EVIDENCE`.

`CURRENT_BRANCH` remains `INSUFFICIENT_EVIDENCE`.

No named reduction or omission policy is created.

## 7. Remaining blockers

- A trusted internal value and an arbitrary caller-supplied value are structurally indistinguishable at the compiler boundary.
- A new provenance marker would be required to distinguish eligible trusted producer output from untrusted input. That is a blocker under this round's design boundary; this document does not design or add it.
- No new runtime value field is shown to be necessary; the missing property is provenance attached to or otherwise structurally associated with the existing values.
- Neither producer path validates a closed deterministic content grammar.
- No component-specific, deterministic, directly testable safe reduction or omission condition has been proven.
- Because candidate eligibility is not proven, the exact stages and fail-closed branches of a future policy remain unresolved.

## 8. Authorization boundary

This document is evidence only. It does not authorize implementation, production changes, test changes, lifecycle or public API changes, request-field changes, telemetry changes, persistence, provider-side reuse, task identity, or a commit. Implementation remains blocked pending project approval. A separate evidence and authorization step would still be required before any named policy or implementation, even if a component were later promoted to `M4_3_CANDIDATE`.

# M4.3 Conservative Operational Context Reduction Plan v1

**Status:** Planning only; blocked pending project approval

## 1. Purpose and frozen boundary

M4.3 asks whether additional explicitly named operational context components can be reduced deterministically while preserving the complete current authority, governance, lifecycle, fallback, provider-boundary, telemetry, persistence, and call-cardinality contracts.

This plan reviews the eight currently known runtime operational-context slots at the current `StageExecutionRequest` / compiler assembly boundary. It does not treat authority or governance as operational merely because those values are provider-facing. Unenumerated artifact, semantic, or runtime keys remain `UNKNOWN` or `MIXED_AUTHORITY` and exact.

The frozen baseline remains:

- `GIT_HISTORY` is the only approved reducible component, under `sdd.git-history.newest8-oldest2-v1`.
- Every other component is exact unless separately approved.
- Authority coverage is 100% and authority byte mismatch is 0.
- `UNKNOWN`, `MIXED_AUTHORITY`, governance, and all other exact-required content remain exact.
- The task coordinate remains `task-absent`; task identity must not be invented or inferred.
- `BASELINE` remains the default; the only public modes are `BASELINE` and `OPTIMIZED`.
- An optimization-specific pre-dispatch failure may fall back to `BASELINE` once. A shared prerequisite failure propagates. No partial optimized dispatch or post-dispatch retry is allowed. At most one provider or subprocess call is allowed per logical execution.
- Providers receive complete self-contained input. Provider-side reuse is unsupported and not authorized.
- Telemetry schema 1.0.4 is unchanged. Persistence, cross-run baseline trust, and provider/session reuse remain forbidden.
- Codex CLI `tokens used` and estimated tokens are not provider evidence.

## 3. Blockers 2 and 3: eligibility and named policy decisions

There are no `M4_3_CANDIDATE` components. Consequently, this plan defines no new reduction policy and does not create implementation slices.

The only applicable named reduction policy remains:

| Component | Policy ID | Exact policy boundary |
| --- | --- | --- |
| `GIT_HISTORY` | `sdd.git-history.newest8-oldest2-v1` | Existing M4.1 behavior only: for a valid, non-empty, newline-safe list of 11-20 lines, each exactly `<40 lowercase hexadecimal hash><TAB><subject>`, retain the newest eight lines and oldest two lines in existing order and insert the exact omitted-entry marker between them. Invalid, empty, at-most-ten-line, or otherwise ineligible values remain exact. |

No policy named "summarize", "trim", "shorten", "use fewer tokens", "drop if large", or an equivalent generic operation is authorized. No token-budget truncation, semantic retrieval, ranking, heuristic selection, arbitrary omission, or duplicate collapse is authorized.

For a future component to become an M4.3 candidate, separate evidence must prove all of the following before project approval: it is non-authority, non-governance, operational, and either unnecessary for the affected stage under an explicit policy or reconstructable/re-fetchable without changing effective semantics; its source/provenance and content boundary are closed and deterministic; ambiguity fails closed to exact; and its named policy is deterministic and directly testable. The current four insufficient-evidence components do not satisfy that gate.

## 4. Blocker 4: authority protection

M4.3 must compare the source protected set with the effective provider input at the existing component coordinates and ordering boundaries. Every `KNOWN_AUTHORITY`, `KNOWN_GOVERNANCE`, `UNKNOWN`, `MIXED_AUTHORITY`, and otherwise exact-required occurrence remains present exactly once, in its required position, with identical canonical UTF-8 bytes.

The mandatory invariants are:

```text
authority_coverage = 100%
authority_byte_mismatch = 0
```

`UNKNOWN` and `MIXED_AUTHORITY` remain fail-closed exact. Governance remains exact. M4.3 permits no authority substitution, semantic equivalent, normalization outside the frozen canonicalization, summarization, transformation, reduction, or omission. A missing, duplicate, reordered, ambiguous, transformed, or byte-mismatched protected occurrence invalidates the optimized candidate before dispatch and requires the existing fallback behavior.

## 5. Blocker 5: stage-aware omission

`.sdd/stages.yaml` is the authoritative source for directly declared `required_inputs`. Its declarations are sufficient to establish positive stage-required relevance for a directly named component. They are not, alone, negative proof that a component is safe to omit when it is not named.

M4.3 therefore adopts this rule:

```text
STAGE_NOT_REQUIRED => NO AUTOMATIC OMISSION
```

Omission would require a separately approved, component-specific named policy that proves the component is a closed non-authority, non-governance operational class, establishes trustworthy provenance, identifies the exact affected stages, and fails closed to exact on any ambiguity. No component meets that standard in this plan. Producer-only association, current request presence, a suggestive key name, or absence from a stage declaration does not authorize omission.

## 6. Blocker 6: task identity

M4.3 does not require task identity. The request has no explicit task coordinate, `tasks.md` is not a current-task identity, and stage metadata or content must not be promoted into task identity.

```text
TASK_IDENTITY_REQUIRED = NO
TASK_COORDINATE = task-absent
```

Any future reduction proposal that requires invented or inferred task identity is blocked and must stop for separate authority.

## 7. Blocker 7: provider-boundary consequence and measurement lenses

The current provider boundary sends a complete self-contained request on every call. Local omission or reduction that changes the selected request before dispatch can therefore reduce the complete provider-bound request bytes; unlike local baseline/delta reuse, the omitted or reduced bytes are not reconstructed into the outbound request. At present, only an eligible `GIT_HISTORY` reduction can produce that effect. Because M4.3 proposes zero new candidates, it authorizes no additional provider-bound byte reduction.

Future evaluation must keep these lenses separate:

- `source bytes`: canonical UTF-8 bytes of all source components before selection or reduction;
- `selected bytes`: canonical UTF-8 bytes selected for the candidate before a component reduction is applied;
- `reduced bytes`: canonical UTF-8 bytes after each authorized named reduction or omission disposition;
- `provider-bound bytes`: directly observed bytes in the complete prepared stdin or HTTP request body at the repository-controlled dispatch boundary; and
- `provider tokens`: valid structured provider input-token usage attributable to that call under schema 1.0.4.

Source, selected, and reduced component bytes are not interchangeable with serialized complete request bytes. Serialization overhead must not be inferred. Provider-bound bytes must be directly observed. Byte differences do not prove token differences. Provider token claims are unauthorized unless valid structured provider usage exists; unavailable usage is not zero. Codex CLI `tokens used`, tokenizer estimates, and other estimates are not provider evidence.

Provider-side cache, reusable handles, session continuation, and baseline/delta transmission remain unsupported and unauthorized.

## 8. Blocker 8: activation and fallback

`BASELINE` remains unchanged and is the default. The public mode vocabulary remains exactly `BASELINE` and `OPTIMIZED`. `OPTIMIZED` means an explicit attempt only and does not guarantee a reduction or optimized dispatch.

An optimized candidate must be wholly prepared and validated before dispatch. An optimization-specific pre-dispatch failure discards it and may dispatch fresh `BASELINE` exactly once. A shared prerequisite failure propagates under existing semantics. Once provider or subprocess dispatch begins, provider and parse/result failures do not permit a `BASELINE` retry. Partial optimized dispatch is forbidden. The maximum provider or subprocess call count per logical execution remains one.

## 9. Blocker 9: future controlled evaluation

No M4.3 candidate currently exists to evaluate. If a later approved amendment promotes any named insufficient-evidence component, its controlled corpus must exercise every exact condition and fail-closed branch of its component-specific policy, including present, absent, empty, malformed, ambiguous-provenance, eligible-stage, and ineligible-stage cases as applicable. It must compare the same logical request under fresh exact `BASELINE` and explicit `OPTIMIZED` attempt.

Mandatory safety evidence for each candidate is:

- authority coverage 100%;
- authority byte mismatch 0;
- semantic regression 0;
- lifecycle regression 0;
- gate regression 0;
- unchanged `BASELINE` compatibility;
- exact fallback and maximum-one-call cardinality;
- no partial optimized dispatch or post-dispatch retry; and
- full repository suite `PASS`.

Efficiency evidence must report, without combining unlike lenses, source bytes, selected bytes, reduced bytes, and complete provider-bound request bytes where directly observable. No arbitrary token or percentage reduction threshold is authorized.

A provider-token comparison is valid only from structured, attributable provider usage accepted under the existing telemetry schema 1.0.4. If it is unavailable, evaluation reports no provider-token claim. Evaluation metadata remains ephemeral, in-memory, or test-local and does not create persistence or a telemetry schema amendment.

## 10. Blocker 10: authorization boundary and unresolved blockers

This document plans M4.3 only. It does not implement M4.3 and does not itself authorize production changes, test changes, implementation slices, or a commit. It does not authorize provider cache/reuse, persistence or cross-run trust, telemetry schema changes, task identity, token-budget truncation, semantic retrieval/ranking, generic summarization, arbitrary omission, or authority summarization/substitution.

Implementation remains blocked pending project approval. In addition, no new reduction can be implemented until at least one explicitly named component has approved evidence resolving its closed classification, trustworthy provenance, safe stage/component-specific policy, fail-closed behavior, and controlled evaluation contract. The unresolved component-specific blockers are:

- `GIT_STATUS`: closed provenance/content validation and a justified useful reduction condition;
- `CURRENT_BRANCH`: closed provenance/content validation and a justified useful reduction condition;
- `BUILD_LINT_TYPECHECK_EVIDENCE_IF_APPLICABLE`: proof that any proposed field or occurrence is non-authority, non-governance, unnecessary or exactly reconstructable, and semantically safe;
- `RELEASE_GIT_IDENTITY`: authoritative stage semantics, closed field/provenance contract, and proof that release-identity semantics are not lost.

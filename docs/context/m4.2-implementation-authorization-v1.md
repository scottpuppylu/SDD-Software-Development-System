# M4.2 Implementation Authorization Proposal v1

## 1. Implementation purpose

This document is an **implementation authorization proposal** for M4.2: Stage/Task-Aware Context Selection and Baseline+Delta Reuse.

It does not authorize itself. Implementation remains blocked until explicit project-authority approval. If that approval is granted, implementation is authorized only through the slices and boundaries defined here. Later slice work still requires validation before commit, and no slice may silently expand authority.

The implementation purpose is to implement M4.2 while preserving all previously approved authority, exactness, lifecycle, fallback, provider-boundary, telemetry, and persistence contracts.

Optimization is conservative and explicit. Default behavior remains `BASELINE`.

## 2. Global implementation invariants

Every slice must preserve:

- authority coverage = 100%;
- authority byte mismatch = 0;
- semantic regression = 0;
- lifecycle regression = 0;
- gate regression = 0;
- exact ordered reconstruction where reconstruction is exercised;
- default `BASELINE` compatibility;
- maximum provider/subprocess calls per logical execution = 1;
- no post-dispatch `BASELINE` retry;
- no partial optimized dispatch;
- optimization-specific pre-dispatch failure -> `BASELINE` once;
- shared prerequisite failure -> existing failure;
- `UNKNOWN` fail-closed exact;
- `MIXED_AUTHORITY` fail-closed exact;
- no task identity invention;
- telemetry schema exactly 1.0.4;
- machine evaluation metadata non-persistent; and
- cross-run baseline/evaluation trust forbidden.

## 3. Explicit non-goals

Implementation must not introduce:

- provider-side cache or provider-side context reuse;
- provider conversation/session continuation;
- persistent context cache;
- persistent baseline registry;
- cross-run baseline trust;
- persistent evaluation state;
- telemetry schema changes;
- new telemetry event types or fields;
- provider/model routing changes;
- new lifecycle states;
- new gate result vocabulary;
- new public compilation modes;
- task identity synthesis;
- semantic retrieval/ranking;
- authority summarization;
- automatic authority truncation;
- token-budget authority omission;
- provider-token savings claims;
- provider-byte savings claims; or
- percentage optimization claims.

Current provider-boundary reuse remains unsupported.

## 4. Implementation slices

Exactly five implementation slices are frozen.

### Slice 1 — Deterministic Selection and Identity Primitives

**Purpose:** Introduce only the deterministic primitives required to represent component identity and planning-approved selection/treatment decisions.

This slice must include only what is necessary for:

- structural component identity under `m4.2-v1`;
- deterministic component ordering;
- exact canonical content identity/digest support;
- component treatment representation;
- conservative stage-aware candidate selection;
- task coordinate remains task-absent;
- fail-closed `UNKNOWN`/`MIXED_AUTHORITY` behavior; and
- no omission of authority-protected components.

This slice must not:

- integrate dispatch;
- create baseline/delta state;
- alter provider calls;
- persist anything;
- change public activation; or
- claim efficiency.

**Exit criteria:**

- focused deterministic tests pass;
- existing behavior is unchanged outside explicit primitives;
- `git diff --check` passes; and
- no persistence, schema, or lifecycle changes occur.

### Slice 2 — Ephemeral Baseline and Exact Delta Reconstruction

**Purpose:** Implement ephemeral single-scope baseline representation, exact delta classification, invalidation, and complete reconstruction.

This slice must include:

- fresh exact baseline only;
- same-scope ephemeral trust only;
- changed, added, removed, reordered, and unchanged categories;
- complete identity/order validation;
- exact ordered reconstruction;
- atomic reconstruction validation; and
- full invalidation on ambiguity, collision, or invalid authority state.

This slice must not:

- dispatch optimized provider calls;
- persist baseline;
- trust cross-run state; or
- introduce cache authority.

**Exit criteria:**

- reconstruction exact-match tests pass;
- authority coverage is 100%;
- authority byte mismatch is 0;
- invalid or ambiguous fixtures fail closed; and
- `git diff --check` passes.

### Slice 3 — Evaluation-Local Measurement and Controlled Corpus

**Purpose:** Implement only evaluation-local M4.2 metrics and deterministic controlled fixtures required by the approved evaluation contract.

This slice must include:

- source, selection, authority, delta, and reconstruction measurements;
- deterministic reuse reason taxonomy;
- controlled corpus;
- semantic, lifecycle, and gate comparison support;
- provider usage validity handling according to schema 1.0.4; and
- provider savings fields unavailable/zero only where factually valid.

This slice must not:

- alter telemetry schema;
- persist machine evaluation metadata;
- claim Codex CLI tokens as provider usage; or
- create `docs/context/m4.2-evaluation-report.md` unless this is final closure.

**Exit criteria:**

- the controlled corpus is deterministic;
- all safety metrics are computable;
- no telemetry schema mutation occurs; and
- `git diff --check` passes.

### Slice 4 — OPTIMIZED Activation and Fallback Integration

**Purpose:** Connect the already validated M4.2 primitives to the existing `OPTIMIZED` path without altering default `BASELINE` behavior or provider-call cardinality.

This slice must preserve:

- public modes `BASELINE` and `OPTIMIZED` only;
- `BASELINE` as the default;
- `OPTIMIZED` means attempt, not guarantee;
- optimization-specific pre-dispatch failure -> `BASELINE` once;
- shared prerequisite failure propagates;
- provider failure after dispatch -> no `BASELINE` retry;
- parse/result failure after dispatch -> no `BASELINE` retry;
- maximum provider/subprocess call count = 1; and
- no partial optimized dispatch.

The current provider boundary still receives complete exact effective input. No provider reuse mechanism may be invented.

**Exit criteria:**

- activation/fallback focused tests pass;
- `BASELINE` compatibility passes;
- one-call cardinality passes;
- Stage08 behavior is unchanged unless separately authorized; and
- `git diff --check` passes.

### Slice 5 — M4.2 Closure Evaluation

**Purpose:** Run the approved controlled evaluation and regression closure after all implementation slices are complete.

This slice must include:

- focused M4.2 tests;
- the full existing regression suite;
- authority coverage validation;
- authority byte-equivalence validation;
- exact reconstruction validation;
- semantic, lifecycle, and gate regression validation;
- default `BASELINE` compatibility;
- fallback/cardinality validation;
- the provider-boundary limitation;
- the provider usage validity result; and
- committed human-readable `docs/context/m4.2-evaluation-report.md`.

Pass requires:

- authority coverage 100%;
- authority byte mismatch 0;
- semantic regression 0;
- lifecycle regression 0;
- gate regression 0;
- reconstruction exact where exercised;
- controlled corpus expected outcomes pass;
- full suite passes; and
- `git diff --check` passes.

Provider savings are not required for pass.

## 5. Slice order and dependencies

The implementation order is frozen as:

`Slice 1 -> Slice 2 -> Slice 3 -> Slice 4 -> Slice 5`

No later slice may be started before the preceding slice has:

- passed its host validation; and
- been committed cleanly.

Parallel implementation is not authorized.

## 6. Commit and validation governance

For every implementation slice:

1. Codex may edit only the explicitly authorized slice scope.
2. Codex must not commit.
3. Host validation must run.
4. Project review must determine `PASS`, `FAIL`, or `INCOMPLETE`.
5. Only `PASS` may be committed.
6. The working tree must be clean before beginning the next slice.

A failed slice must be corrected within that slice. Scope must not be broadened to fix unrelated architecture or style issues.

## 7. Stop conditions

Implementation must stop and return for authority review if any of these occur:

- authority conflict;
- a requirement requires changing an approved Blocker 1-10 decision;
- a telemetry schema change appears necessary;
- persistence appears necessary;
- task identity would need to be invented;
- provider-specific reuse is required;
- public activation vocabulary would need to change;
- lifecycle or gate semantics would need to change;
- provider/subprocess call cardinality would increase;
- implementation requires a sixth slice or material scope expansion; or
- exact authority coverage/equivalence cannot be maintained.

Such issues must not be solved by inference.

## 8. Implementation authorization boundary

If explicitly approved by project authority:

- Slice 1 through Slice 5 become authorized in the defined order;
- each slice remains bounded by its own scope;
- implementation may not exceed the global invariants or non-goals; and
- no other M4.2 capability becomes authorized.

This proposal does not authorize itself. Before explicit project-authority approval, M4.2 implementation remains blocked. After approval, implementation is authorized only through the slices and boundaries defined here. Later slice work still requires validation before commit. No slice may silently expand authority.
